## 六、性能优化与稳定性保障

> **这一章的作用**：面试官问"你做过什么优化"，其实想看两件事——**你会不会定位瓶颈**，以及**你知不知道自己选的手段有什么代价**。
> **讲法**：先说 6.1 的三类思路（20 秒），再从表里挑 2-3 项展开。
> ⚠️ **口径提醒**：带「文档记录」的是项目文档里已有的数字；其余为「本地自测」或「估算」，**说的时候一定要带上口径**。

### 6.1 先给框架：我的优化只有三类思路（背这段，比背 12 条优化有用）

> "我的优化基本可以归成三类：
> **第一类是把串行改成流式并行**。语音链路原本是"等大模型把整段回复写完 → 再整段送去合成 → 才能播"，这条链上是三段串行等待；我改成流式拿 token、凑够一句就送去合成，而且多句并发合成，用户听到第一句话的时间从秒级压到毫秒级。
> **第二类是把同步改成异步**。文档解析和向量化原来是在请求线程里做完才返回，一个几十页 PDF 会让接口转很久；我改成投递到 Redis Stream，接口立刻返回，前端轮询任务状态。
> **第三类是把不可控的东西交给代码控制**。大模型输出长度不可控、并发数不可控、用户请求量不可控，所以我用配置项约束输出长度、用信号量限制并发、用 Lua 脚本做原子限流——**凡是"靠模型自觉"或"靠运气"的地方，我都尽量换成确定性代码。**"

### 6.2 12 项优化逐条拆解（每项都回答：这是什么技术 / 解决什么问题 / 前后对比 / 代价）

| # | 优化手段（技术是什么） | 解决什么问题 | 优化前 → 优化后 | 口径 | 代价 / 副作用 |
|---|---|---|---|---|---|
| 1 | **流式 LLM + 句子级并发 TTS**：大模型逐 token 吐出内容，凑够一个句子就立刻送去合成语音，不等全文 | 语音 AI"开口慢"，用户等好几秒才听到第一个字 | TTS 首包 ~500ms → **200ms** | 文档记录（−60%） | 并发合成要保证播放顺序；并发数不控制会撞供应商限流 |
| 2 | **DashScope Qwen3 实时 ASR + 服务端 VAD**：VAD 是"语音活动检测"，服务端靠静音时长判断你说完没有 | 断句慢，用户说完要等一段才出字幕 | 断句 ~800ms → **400ms** | 文档记录（−50%） | 静音阈值极其难调：调小会打断用户，调大会显得迟钝 |
| 3 | **统一 16kHz PCM 采集**：ASR 模型要求 16k 单声道 PCM，前端用 AudioWorklet 做重采样 | 识别质量差、格式不匹配 | ~90% → **95%+** | 文档记录（+5%+） | 前端多一个 worklet 文件要跟着打包；不同浏览器采样率行为要兜底 |
| 4 | **约束输出长度**：`ai-question-max-chars: 120` + prompt 要求 2-4 句、禁 Markdown | 模型偶尔长篇大论，用户等太久，不像真人对话 | 不可控长文 → 单轮 2-3 个 TTS 片段 | 实现约束 | 复杂问题可能被压得太短，需要 prompt 里给"可以分两轮问"的出口 |
| 5 | **异步化（Redis Stream 管道）**：接口只负责投递消息，后台消费者慢慢处理 | 上传大文件阻塞请求线程，接口转圈 | 同步解析 → **接口 RT 与文件大小解耦** | 本地自测 | 需要任务状态与失败终态，用户要能感知"还在处理" |
| 6 | **`React.lazy` 路由级分包 + `manualChunks`**：把每个页面拆成独立 JS 文件，首屏只下载当前页面 | 前端首屏体积大 | 单包全量加载 → **按路由按需加载** | 实现事实 | 切路由时多一次网络请求；分包过细反而变慢 |
| 7 | **`react-virtuoso` 虚拟列表**：只渲染可视区内的 DOM 节点 | 历史记录、知识库长列表渲染卡顿 | 全量 DOM → 只渲染可视区 | 实现事实 | 需要预估行高，滚动定位偶尔跳动 |
| 8 | **`@RateLimit`（`@Repeatable` 多维度）+ Lua 原子限流**：滑动窗口与令牌桶的混合实现，一次 Redis 往返完成 | 并发请求打爆下游、接口被刷 | 普通 Redis 命令**并发下超额放行** → **精确限流** | 本地自测 | 每个受限接口多一次 Redis 调用；Lua 脚本不好调试 |
| 9 | **Java 21 虚拟线程**（`spring.threads.virtual`）：IO 等待时释放底层载体线程 | 阻塞式模型下高并发连接成本高 | 平台线程受池大小限制 → 虚拟线程可承载大量 IO 等待型请求 | 实现事实 | **`synchronized` 块内阻塞会让虚拟线程"钉住"载体线程**（pinning），所以共享状态我优先用 `ReentrantLock` |
| 10 | **Redis 缓存活跃会话**：把进行中的面试会话状态放内存 | 每一轮对话都去查库 | 每轮查库 → 内存读取，状态变更时写回/失效 | 文档记录 | 缓存与库的一致性要靠"变更即失效"（我封装了 `invalidateSessionCache`） |
| 11 | **开场音频缓存 `openingAudioCache`**：开场白是固定文案，合成一次反复用 | 重连或重进会话时重新合成开场白 | 每次重合成 → 命中缓存直接复用 | 实现事实 | 内存占用；多实例部署时缓存不共享（当前单实例无影响） |
| 12 | **`Semaphore` 并发闸门 + 单句 8s 超时**：限制同一会话同时在合成的句子数 | 长回复瞬间打出大量 TTS 请求，可能被限流、播放乱序 | 可能被供应商限流 → 稳定 2-3 并发在流 | 实现事实 | 并发上限太小会排队、反而抬高首包延迟，要和超时兜底配合 |

**一句话总结（背这句）**
> "我的优化基本围绕三个方向：**把串行改成流式并行**（语音链路）、**把同步改成异步**（文档处理）、**把不可控的交给代码控制**（输出长度、并发数、限流、配额）。"

### 6.3 语音链路的延迟拆解（面试官爱问"你怎么定位瓶颈"）

> 我的定位方法很朴素：**先知道延迟由哪几段组成，再逐段量。**
>
> ```
> 用户松口  →  前端 200ms 分块上传  →  ASR 出文本  →  LLM 首 token  →  TTS 首包  →  浏览器开始播放
>                (网络+编码)            (断句延迟)      (生成延迟)        (合成延迟)
> ```
> 我的判断顺序：
> 1. **先怀疑"等全文生成完"**——这是最大的一块，而且**是架构问题不是参数问题**，所以先改成流式；
> 2. **再量 TTS 首包**——这是用户"听到声音"的最后一公里，所以做了句子级并发合成；
> 3. **最后才调参数**（VAD 静音阈值、debounce）——**参数只能微调体验，改不了架构级延迟**。
>
> **这段话的价值在于展示"优化顺序的判断"**：先做架构级优化（收益大、风险可控），再调参数（收益小、容易反复）。

### 6.4 稳定性兜底清单（**这一节面试官特别爱听，因为它体现"你想过线上会怎么坏"**）

| 故障场景 | 兜底方案 | 关键参数 |
|---|---|---|
| LLM 返回格式不对 / 偶发失败 | 结构化输出**重试** | `structured-max-attempts: 2` |
| 结构化输出重试后仍失败 | **降级**：返回可用的部分结果 / 代码聚合兜底 | 评估汇总失败回退代码聚合 |
| 异步任务（向量化/简历分析/评估）失败 | **最多重试 3 次 → 标记 FAILED**，状态可查 | 3 次 |
| 消费者拿到"实体已不存在"的消息 | **先校验实体存在，不存在直接 ACK 丢弃** | 防脏消息无限重试 |
| TTS 单句卡住 | **单句超时 8s**；前端**播放看门狗**（按 WAV 头算时长 + 1.5s，上限 60s）自动跳过 | `tts-timeout-seconds: 8` |
| ASR 连接断开 | `restartTranscription` 重连，**每 10s 检查、最多 2 次**；重连期间音频直接丢弃且**不报错** | 最多 2 次 |
| 某一次评估批次失败 | **只丢该批 + 记录 error**，其余批次正常；**缺位题按 0 分占位** | 保证统计口径不变形 |
| 单轮对话没有可用的历史 | **历史为空才发开场白**；开场音频进缓存 | 防重复寒暄 |
| 前端断线/刷新 | 会话状态**从数据库恢复**；组件卸载自动 pause 未结束会话 | 防状态永远 IN_PROGRESS |
| 密钥无效 / 鉴权失败 | 多 Provider 可切换（`llmProviderRegistry` 支持百炼/Kimi/DeepSeek/GLM/本地 LM Studio） | ⚠️ 已知缺陷：**鉴权失败被当成解析失败去重试**，应快速失败 |
| 接口被异常流量打爆 | **多维度限流**兜住入口，保护下游和 AI 配额 | GLOBAL/IP/USER |
| 后端抛任何异常 | **全局异常处理器统一返回 HTTP 200 + `Result.error(code, message)`** + 10 域错误码 | 前端**永远不会白屏/解析失败** |
| 服务启动顺序错乱 | docker healthcheck（`pg_isready` / `redis-cli ping` / `minio curl`）+ `depends_on: service_healthy` | 保证依赖真的可用再启动 app |
| 容器部署下语音 WS 连不上 | ⚠️ **已知缺陷**：nginx 缺 `/ws/` location 与 Upgrade 头 → 需补 nginx 配置 | 我主动承认 |
| **接口没有鉴权** | ⚠️ **已知缺口**：没有 Spring Security，`userId` 写死为 `"default"`（`VoiceInterviewService.java:58`） | 单机自部署定位下的取舍，改造方案见 2.19 |

**"稳定性三句话"（总结用）**
> 1. **外部依赖全部当"会失败"处理**：LLM、TTS、ASR、对象存储都配了超时 + 重试 + 降级；
> 2. **异步任务必须有终态**：要么成功，要么 FAILED，**绝不允许"永远卡在处理中"**；
> 3. **失败不能污染统计**：缺位按 0 分占位、单批失败只丢该批——**保证"失败"不会意外变成"分数更高"**。

### 6.5 可观测性（诚实说明现状）

**已做**
> - **结构化日志**（SLF4J，异常作为最后一个参数，`AGENTS.md` 明文禁止 `log.error("Error: {}", e.getMessage())` 这种丢失堆栈的写法）；
> - **关键指标埋点**：语音链路埋了 LLM **首 token 延迟**等指标（如 `app.voice.interview.llm.first_token_latency`），因为**首 token 延迟才是用户感知的核心指标**，而总耗时会被长回复稀释；
> - **健康检查**：postgres / redis / minio 都有 healthcheck。

**没做（主动说）**
> - **没有 CI**：`app/Dockerfile` 构建时 `-x test` **跳过测试**，也没有流水线在合并前跑测试——**这是工程化上最大的缺口**；
> - **app 容器自己没有 healthcheck**，编排只能判断依赖是否健康，判断不了应用是否可用；
> - **没有接入 Prometheus/Grafana**，指标目前只能看日志。

> **这段话术的用法**：说完"已做"之后主动接"没做"，然后立刻给方案——
> "**我知道的改法是：加 GitHub Actions（build + test + 镜像构建）、给 app 加 healthcheck（或 Spring Boot Actuator 的 `/actuator/health`）、指标接 Micrometer 暴露到 Prometheus。**"
> **面试官要的不是"你什么都做了"，而是"你知道差在哪、知道怎么补"。**
