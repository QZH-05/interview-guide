### 2.9 WebSocket：为什么语音必须用长连接

**是什么**
- WebSocket 是一条 TCP 长连接上的"双向对讲机"。比喻：HTTP 是寄信（一次问一次答，投完就完事）；WebSocket 是打电话（拨通一次，双方随时都能开口，不用重新拨号）。
- 术语首现解释：**全双工**＝同一时刻两端都能发数据，不是"我说完你才能说"。
- **握手（handshake）**：拨号的过程。浏览器先发一个"伪装成 HTTP"的 GET 请求，带 `Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key` 三个头；服务器同意就回 `101 Switching Protocols`，从这一刻起同一条 TCP 连接不再说 HTTP，改说 WebSocket 帧。只有这一次用到了 HTTP，之后都是 WS 帧。

**解决什么问题**
- HTTP 请求-响应是"拉"模型：客户端不主动问，服务器没法把消息塞给你。语音面试要同时干两件事——前端持续把麦克风音频推上去、后端持续把字幕和 AI 语音推下来。这是双向流，HTTP 天然做不到。
- 没有它会怎样：只能轮询或者用两条通道，延迟和开销都不可接受。
- 一张表把差别摆平（面试直接照这个说）：

  | 维度 | HTTP 请求-响应 | WebSocket |
  |------|----------------|-----------|
  | 连接 | 一问一答，短连接（Keep-Alive 也是复用请求） | 一次握手后长连接常驻 |
  | 方向 | 只能客户端先问 | 全双工，双方随时发 |
  | 每次开销 | 每个请求都带完整请求头/响应头 | 只有 2~14 字节的帧头 |
  | 服务端能否主动推 | 不能 | 能 |
  | 本项目用途 | 建会话、拉历史消息、结束会话（`/api/...`） | 推音频、收字幕和 AI 语音（`/ws/voice-interview/{sessionId}`） |

- 补一个术语：WS 跑起来之后传的都是**帧（frame）**，分数据帧和控制帧（`ping`/`pong`/`close`）。控制帧就是协议自带的心跳工具——本项目**没用**它，这条在下面"代价 3"里说。

**本项目怎么用**
1. 后端注册端点：`app/src/main/java/interview/guide/modules/voiceinterview/config/WebSocketConfig.java:22-27`
   ```java
   registry.addHandler(voiceInterviewWebSocketHandler, "/ws/voice-interview/{sessionId}")
           .addInterceptors(new HttpSessionHandshakeInterceptor())
           .setAllowedOrigins(corsProperties.getAllowedOrigins().split(","));
   ```
   `{sessionId}` 是路径变量，一个面试会话一条连接；握手期间还会顺手把 HTTP Session 复制过去（`HttpSessionHandshakeInterceptor`，:25）；跨域白名单来自 `cors.allowed-origins`，默认 `http://localhost:5173,http://localhost:5174,http://localhost:80`（`app/src/main/resources/application.yml:193`）。
2. 连接上限调大：`WebSocketConfig.java:29-35` 把文本/二进制消息缓冲都设成 2MB（`setMaxTextMessageBufferSize`/`setMaxBinaryMessageBufferSize`），否则一块 base64 音频就超默认 8KB 被断开。
3. 处理器：`VoiceInterviewWebSocketHandler extends TextWebSocketHandler`（`app/.../handler/VoiceInterviewWebSocketHandler.java:57`）。建连时 `afterConnectionEstablished`（:142-172）做四件事：把消息大小限制压到 256KB、用 `ConcurrentWebSocketSessionDecorator(session, 10s, 512KB)` 包一层防并发写、启动 ASR、发 welcome。
4. 消息格式（**以代码为准**）：
   - 客户端 → 服务端音频：`{type:'audio', data:<base64>, timestamp}`，见 `frontend/src/api/voiceInterview.ts:339-351`
   - 客户端 → 服务端控制：`{type:'control', action, data, timestamp}`，见 `frontend/src/api/voiceInterview.ts:356-369`；`action` 有三个值：`submit`（用户手动提交本轮）、`end_interview`、`start_phase`（`VoiceInterviewWebSocketHandler.java:869-893`）
   - 服务端 → 客户端有 6 种，且**全部是小写字符串**：`subtitle`(:897)、`audio`(:912)、`text`(:924)、`audio_chunk`(:956)、`control`(:943)、`error`(:931)
   - ⚠️ `docs/voice-interview-architecture.md` 里写的 `AUDIO | SUBTITLE | CONTROL` 大写命名**和代码不一致**，代码里是小写 `audio | subtitle | control`。背的时候说小写。
5. 服务端分派：`:302-351` 先 `objectMapper.readTree(payload)` 再 `msg.get("type").asText()` 走 `switch(type)`；`audio` 只打 trace 日志（避免刷屏）、>200KB 记 warn；`control` 反序列化成 `WebSocketControlMessage` 再进 `handleControl`。
6. 出口闭环：前端 `VoiceInterviewPage.tsx:547` 和 `:608` 拿 `session.webSocketUrl` 建连，`connectWithHandlers` 注册 `onSubtitle/onAudioChunk/onControl` 等回调，后端的 `sendSubtitle`(:895-901)、`sendTextMessage`(:918-928)、`sendAudioChunk`(:950-962) 就是这条线上的返回值。
7. 前端客户端类：原生 `new WebSocket(url)` 被包了一层，就是 `frontend/src/api/voiceInterview.ts:247-409` 的 `VoiceInterviewWebSocket`。`connect()`（:263-334）里用一个 `switch (message.type)` 分发前面说的六种下行消息，外部只看到回调。
8. 断线重连（前端唯一的一层防线）：`maxReconnectAttempts = 3`、`reconnectDelay = 2000`（`voiceInterview.ts:251-253`）——`onclose` 时只要**不是主动关闭**且没超过 3 次，就 2 秒后重连（:263-334）；反过来，用户主动断开时它先把 `reconnectAttempts` 拉满再 `close(1000)`（:374-381），这样重连逻辑不会被自己误触发。这是个小而巧的写法，值得记。
9. 服务端侧还有一层"兜底收尾"：`afterConnectionClosed`（`VoiceInterviewWebSocketHandler.java:366-393`）除了清理 session、中断正在跑的语音流水线、停掉 ASR，还会调 `interviewService.endSessionIfInProgress(sessionId)` —— 用户直接关页面时把会话状态从 IN_PROGRESS 收掉，否则这条会话会永远卡在"进行中"，列表里一直挂着。

**为什么选它 + 代价**
- 为什么不用轮询：音频一块 200ms（见 2.10），每秒 5 个 HTTP 请求，每个请求都要带完整请求头/重建连接、还可能乱序。延迟和带宽双重浪费。
- 为什么不用 SSE：SSE 是**单向**的（只能服务器 → 浏览器），上行还得另开 HTTP。双向场景用它等于拆成两条链路，纯找麻烦。
- 代价 1（真实缺陷，可以被追问）：**容器部署下 nginx 没代理 `/ws/`**。`frontend/nginx.conf:15-30` 只有两个 location——`/` 的 SPA fallback（:15-17）和 `/api/` 的反代（:19-30），**没有 `/ws/`，也没有 `Upgrade`/`Connection` 头**。结果：走前端容器 `http://localhost:80` 访问时，WebSocket 请求根本到不了后端，只有本机直连 `ws://localhost:8080` 才通。修法：
  ```nginx
  location /ws/ {
      proxy_pass http://app:8080;
      proxy_http_version 1.1;
      proxy_set_header Upgrade $http_upgrade;
      proxy_set_header Connection "upgrade";
      proxy_read_timeout 3600s;
  }
  ```
  架构文档里写"支持 WebSocket 代理"是目标态，不是当前态。
- 代价 2：**WS 地址是硬编码的**。`app/src/main/java/interview/guide/modules/voiceinterview/service/VoiceInterviewService.java:537` 直接 `String.format("ws://localhost:8080/ws/voice-interview/%d", ...)` 塞进 `SessionResponseDTO.webSocketUrl`，没有配置项、没有环境变量覆盖；前端 `VoiceInterviewPage.tsx:547/:608` 还写了同样的兜底。容器里浏览器访问自己的 localhost:8080 = 必失败。改法：抽成 `app.voice-interview.websocket-base-url` 配置，或前端用 `window.location` 拼相对路径。
- 代价 3：**没有 WS 层心跳**。全仓找不到 ping/pong；只有业务层 `lastActivityTime`(:83) + `WARNING_TIME_MS` 4.5 分钟(:84) + `PAUSE_TIMEOUT_MS` 5 分钟(:85) 的定时检查(:1131-1135)。中间隔着 nginx 或云负载均衡时，空闲连接会被静默掐断。
- 替代方案 WebRTC：真正该用的技术（端到端、天然抗弱网、能省掉服务端中转那一跳），代价是要自建信令、STUN/TURN、还要临时凭证 STS。本项目为了简单选了"WS 传 base64 音频"，属于用工程复杂度换上手速度。

### 2.10 浏览器音频采集：从麦克风到 16kHz PCM

采集链路全部在 `frontend/src/components/AudioRecorder.tsx` 的 `startRecording()`（:135-273）里。按数据流顺序拆开是 9 个关键点（①~⑨），外加一个旁路的音量动画（⑩）。

先给一句话全貌，后面再逐个展开：
- **`getUserMedia` 拿到麦克风流 → `createMediaStreamSource(stream)` 把流接进音频图 → `AudioWorkletNode`（重采样 + 切块 + float32→int16 全在这里面）→ `GainNode(gain=0)` 哑掉 → `audioContext.destination`**；旁边另挂一个 `AnalyserNode`，只用来画音量光圈。
- 另一边，`MediaStream` 还同时交给了 Silero VAD 做本地语音活动检测（见 2.11）。同一条流被两处复用，不会再弹一次麦克风权限。

**① getUserMedia：向浏览器要麦克风权限**
- **是什么**：浏览器提供的取流 API，`navigator.mediaDevices.getUserMedia({audio:true})` 返回一个 `MediaStream`（可以理解成"麦克风的水龙头"）。权限弹窗就是它触发的。
- **解决什么问题**：没有它，网页拿不到任何音频；早年的 `navigator.getUserMedia` 已废弃，现在必须用 `mediaDevices` 这个新命名空间。
- **本项目怎么用**：`AudioRecorder.tsx:148-155`
  ```ts
  const stream = await navigator.mediaDevices.getUserMedia({
    audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true, sampleRate: 16000 },
  });
  ```
  注意这里传的是一个**约束对象（constraints）**，不是命令。浏览器可以不完全满足你，尤其是 `sampleRate`。
- **为什么选它 + 代价**：这是唯一入口，没得选。坑在于约束是"建议"：`sampleRate: 16000` 在多数桌面 Chrome 上会被忽略、实际给 48kHz，所以后面必须自己重采样（这就是 AudioWorklet 存在的理由）。

**② 三个开关：echoCancellation / noiseSuppression / autoGainControl**
- **是什么**：浏览器内置的三种音频前处理。`echoCancellation`＝回声消除（把扬声器放出来的声音从麦克风信号里减掉，学术名叫 AEC）；`noiseSuppression`＝降噪（压掉风扇、空调那种稳态底噪）；`autoGainControl`＝自动增益（声音小就自动放大，让人声电平稳定）。
- **解决什么问题**：没有它们，AI 说话时扬声器的声音会被麦克风录回去，再送去 ASR 就变成"AI 自己跟自己对话"；底噪大时 VAD 会误判成有人说话。
- **本项目怎么用**：`AudioRecorder.tsx:150-152` 三个全开 `true`。
- **为什么选它 + 代价**：零成本（浏览器白送），代价是**治标不治本**——不戴耳机、音量又开得大的时候，回声还是会泄漏进来。所以本项目在上面又叠了三层防护：前端门控（`VoiceInterviewPage.tsx:641`）、服务端冷却期（`VoiceInterviewWebSocketHandler.java:89` 的 `AI_SPEAK_COOLDOWN_MS = 800` 与 :487-491 的丢弃）、处理中丢弃迟到定稿（:605）。彻底解法只有戴耳机或上 WebRTC。

**③ Web Audio API / AudioContext：浏览器的音频处理流水线**
- **是什么**：`AudioContext` 是整条音频流水线的"调音台"。你在上面创建各种**节点（node）**——声音源、滤波器、分析器、输出口——然后用 `connect()` 把它们串成一条链。
- **解决什么问题**：没有它，你只能拿到一坨压缩音频文件，没法做逐帧处理（重采样、音量分析、静音），也没法精确控制采样率。
- **本项目怎么用**：`AudioRecorder.tsx:196` `new AudioContext({ sampleRate: TARGET_SAMPLE_RATE })`（`TARGET_SAMPLE_RATE = 16000`，:52）；:201 `createMediaStreamSource(stream)` 把麦克风流变成源节点。整条链在 :254-256：
  ```
  source → workletNode('pcm-processor') → gainNode(gain=0) → audioContext.destination
  ```
- **为什么选它 + 代价**：这是浏览器唯一能做原始音频处理的底层 API。代价：`AudioContext` 需要用户手势（点一下页面）才能 `resume()`，且每个标签页能开的实例数有限；本项目一共开了两个——采集用 16kHz（`AudioRecorder.tsx:196`），播放用 24kHz（`VoiceInterviewPage.tsx:170`）。

**④ PCM：音频的"裸数据"格式**
- **是什么**：Pulse Code Modulation（脉冲编码调制）。比喻：MP3/WebM 像压缩包，PCM 像解压后的原始文件——只是一串数字，每个数字表示"某一瞬间声音波形的高度"。不含任何压缩、不含头信息，拿去就能用。
- **解决什么问题**：ASR 服务要的是连续的采样点，给它 MP3 还得先解码，没法边录边传。
- **本项目怎么用**：格式是 **16 位有符号整数、单声道、16kHz**（16-bit signed PCM, mono, 16kHz），写完编码后 base64 塞进 WS 的 `data` 字段。后端 `QwenAsrService.sendAudio`（`app/.../service/QwenAsrService.java:340-369`）只做一次 base64 解码就直接 `appendAudio`，中间没有任何转码——说明前端产出的必须已经是 PCM16LE。这个格式在 `application.yml:235-236`（`format: pcm`、`sample-rate: 16000`）和 ASR 参数里对齐。
- **为什么选它 + 代价**：无损、零延迟、边录边发；代价是**体积大**——16kHz × 16bit = 256 kbps，一秒 32KB，是 Opus 的十倍以上。这也是为什么必须配 WebSocket 长连接（2.9），不然传输开销会炸。

**⑤ 采样率 16kHz 与重采样**
- **是什么**：采样率＝每秒取多少个点。16kHz 就是每秒 16000 个点。**重采样（resampling）**＝把某个采样率的信号换算成另一个采样率，比喻：把 48 帧/秒的视频转成 16 帧/秒。
- **解决什么问题**：麦克风硬件固定给 44.1kHz 或 48kHz，但 ASR 只认 16kHz。不转换就是"鸡同鸭讲"，识别结果会变成一团噪音（音调全错、语速全错）。
- **本项目怎么用**：转换在 AudioWorklet 里做。`frontend/public/audio-worklet/pcm-processor.js:31` 调 `this.resample(input, sampleRate, this.targetSampleRate)`——这里的 `sampleRate` 是 AudioWorkletGlobalScope 提供的**全局变量，就是当前 AudioContext 的真实采样率**，不是写死的。算法是**线性插值**（:46-64）：
  ```js
  const ratio = sourceRate / targetRate;
  const sourceIndex = i * ratio;
  const lower = Math.floor(sourceIndex);
  output[i] = input[lower] * (1 - weight) + input[upper] * weight;
  ```
  另外有个细节：如果真实采样率已经是 16000，:47-49 直接 `return input` 跳过。
- **为什么选它 + 代价**：线性插值够快够简单（音频降采样对音质要求不高，反正后面是给模型听的）。代价：**不做抗混叠滤波**，48k→16k 时高频会折叠回可听频段（aliasing），理论上会有金属音。工程上可接受，但被追问"重采样为什么不用 sinc/多相滤波"要答得出来。也正因为 AudioContext 请求 16kHz 是"建议"，这个 worklet 重采样本质是**保险丝**——浏览器给了 16k 就是空转，给了 48k 就真干活。

**⑥ float32 → int16**
- **是什么**：Web Audio 内部一律用 **float32**（每个采样点是 -1.0 ~ 1.0 的小数），而 PCM/ASR 要的是 **int16**（-32768 ~ 32767 的整数）。这一步就是把小数映射成整数。
- **解决什么问题**：不转的话，按 int16 解读 float32 的内存会得到纯噪声。
- **本项目怎么用**：`pcm-processor.js:71-78`
  ```js
  const s = Math.max(-1, Math.min(1, input[i]));
  output[i] = s < 0 ? s * 0x8000 : s * 0x7fff;
  ```
  先钳位（clip）到 [-1,1] 防溢出，再用**不对称缩放**：负数乘 `0x8000`(32768)、正数乘 `0x7fff`(32767)——因为 int16 负半轴比正半轴多一个值。
- **为什么选它 + 代价**：这是 Web Audio 与 PCM 之间的标准转换。代价：**有量化误差**，理论上信噪比上限约 96dB；语音识别完全够用。

**⑦ AudioWorklet 与 pcm-processor.js：在音频线程里干活**
- **是什么**：`AudioWorklet` 让你把一段自定义 JS 注册成一个音频节点，跑在浏览器专门的**音频线程**上，每 128 个采样（一帧，约 2.7ms）被回调一次。`registerProcessor('pcm-processor', PcmProcessor)`（`pcm-processor.js:132`）就是给它起名字。
- **解决什么问题**：主线程要渲染 UI、跑 React，一旦卡顿（掉帧），音频处理跟不上就会爆音/丢包。放音频线程就不受 UI 影响。
- **本项目怎么用**：:223-224 `audioContext.audioWorklet.addModule('/audio-worklet/pcm-processor.js')` → :234 `new AudioWorkletNode(audioContext, 'pcm-processor')` → :239-246 用 `workletNode.port.onmessage` 收数据、转 base64、`onAudioData(base64)` 发出去。这个文件放在 `frontend/public/` 下，是**静态资源**，Vite 不打包它（原样拷到根路径 `/audio-worklet/pcm-processor.js`）。
- **为什么选它 + 代价**：比起被废弃的 `ScriptProcessorNode`，它是唯一被标准认可的方案。代价：worklet 里**不能用 DOM、不能 import 普通模块**，和主线程只能靠 `postMessage` 通信（本项目在 :119 传的是 `chunk.buffer`，用 transferable 的拷贝模式）；而且必须由 `addModule()` 异步加载，加载失败整条链就断（:143-145、:197-200 有兜底抛错）。

**⑧ 3200 采样 = 200ms 一块**
- **是什么**：`pcm-processor.js:16` `this.samplesPerChunk = 3200;`。16kHz × 0.2 秒 = 3200 个采样点，所以一块正好 200ms、6400 字节。
- **解决什么问题**：不能每个采样点发一次（16kHz 的消息频率，WS 直接跪），也不能攒 5 秒发一次（延迟不可接受）。200ms 是延迟与开销的折中。
- **本项目怎么用**：`pcm-processor.js:92-123` `flushChunks()` 用一个 pending 数组累积，够 3200 就切一块 `this.port.postMessage(chunk.buffer)`，并且做了跨块拼接（:97-115，上一块的尾巴和这一块的头能接上，不会因为 128 帧边界对不齐丢样本）。主线程收到后 `AudioRecorder.tsx:244-245` 立刻 base64 + `onAudioData`。
- **为什么选它 + 代价**：200ms 对 ASR 是合适的粒度。代价：固定的 200ms 意味着**最坏情况多 200ms 延迟**；且单块 6400 字节 base64 后约 8.5KB，1 小时面试累计上行量相当可观（也解释了为什么需要 `MAX_ASR_READY_RETRY` 那种穷举式的重连容错）。

**❌ 为什么不用 MediaRecorder（关键选型）**
- **是什么**：`MediaRecorder` 是浏览器另一套录制 API，直接给你录制好的文件（WebM/Opus）。比喻：它是"录音笔"，按下开始、停止时给你一个文件。
- **解决什么问题**：适合"录完再上传"的场景（比如上传一段语音留言）。
- **本项目为什么不用**：它产出的是**压缩容器格式**（webm/opus），需要攒够一段、封包、最后还是自己解码成 PCM 才能喂 ASR——等于绕一圈。实时流式 ASR 要的是"录到哪传到哪"的裸 PCM。全仓搜索 `MediaRecorder` **零命中**（已验证），这条是干净的选型决策。
- **代价**：自己实现采集就必须自己处理重采样、编码、分块、资源释放（`AudioRecorder.tsx:54-117` 那一长串 cleanup 就是代价），复杂度明显更高。

**❌ 为什么不用已废弃的 ScriptProcessorNode**
- **是什么**：AudioWorklet 之前的老方案，也能拿音频数据回调。
- **解决什么问题**：历史遗留。
- **本项目为什么不用**：它在**主线程**跑回调，主线程一卡就丢帧→声音断续有杂音；而且已经被 Web Audio 标准标记为 deprecated，随时可能被移除。全仓搜索 `ScriptProcessorNode`/`createScriptProcessor` **零命中**（已验证）。
- **代价**：AudioWorklet 写起来麻烦——独立文件、不能共享作用域、要 `addModule` 异步加载、报错难调试。

**⑨ gainNode.gain = 0：哑音节点（防回声的关键一手）**
- **是什么**：`GainNode` 是音量旋钮，`gain.value` 是倍数。设成 0 就是**彻底静音**。
- **解决什么问题**：麦克风的源节点必须接到 `audioContext.destination`（音频图的终点）才能保证整条链被浏览器持续驱动、回调持续触发。但这样麦克风听到什么就会原样放出来——变成一只"扩音喇叭"，AI 的声音再被录进去，自激振荡。
- **本项目怎么用**：`AudioRecorder.tsx:248-256`
  ```ts
  const gainNode = audioContext.createGain();
  gainNode.gain.value = 0; // Mute output
  source.connect(workletNode);
  workletNode.connect(gainNode);
  gainNode.connect(audioContext.destination);
  ```
  数据先经过 worklet 被取走，再流进音量 0 的 gain 节点流到终点——**用一根哑掉的尾巴保住音频图活着**。注意 AI 语音的播放走的是另一个 AudioContext（`VoiceInterviewPage.tsx:170`），跟这条链毫无关系，所以哑音不会让 AI 没声音——这是最容易被面试官追问的点。
- **为什么选它 + 代价**：一行代码解决鸣叫问题，没有替代方案的性价比更高。代价：它是**软件层面**的，管不住物理泄漏（扬声器 → 空气 → 麦克风），所以还得叠 2.9 里说的门控与冷却期。

**⑩ AnalyserNode：音量动画**
- **是什么**：`AnalyserNode` 是"频谱探针"，能实时吐出当前音频的频谱数据（`getByteFrequencyData`），你拿它算音量。
- **解决什么问题**：用户不知道麦克风到底有没有在工作。没有反馈，他会对着屏幕自言自语还不确定。
- **本项目怎么用**：`AudioRecorder.tsx:204-206` 创建 `analyser.fftSize = 256` 并 `source.connect(analyser)`；:212-220 每 100ms 取一次频谱、求平均值 `setVolume(average)`；:316-325 用这个 volume 画一圈会随音量缩放的呼吸光圈（`width: 100 + (volume/255)*100` %，透明度同时衰减）。
- **为什么选它 + 代价**：`AnalyserNode` 是内置节点，零成本、不占额外计算。代价：**它只是装饰**（`volume` 不参与任何业务判断），且 100ms 一次的 `setInterval` + `setState` 会让页面每秒重渲染 10 次，是个小性能税。

### 2.11 VAD 与 Silero 模型

**VAD 是什么**
- 全称 Voice Activity Detection，**语音活动检测**。一句话：判断"这段音频里现在有没有人在说话"。比喻：一个门卫，不关心你说什么，只关心"有没有人在说"。
- 术语首现解释：它输出的是**布尔量 + 时间边界**（哪一毫秒开始有声、哪一毫秒结束），不输出文字。出文字的是 ASR（见 2.12），两者完全不同的东西——这是最容易混的两件事。

**解决什么问题**
- 没有它：麦克风永远在推流，静音段也照传，白烧带宽和 ASR 调用时长；而且**没法知道用户说完了没有**——只能靠固定时长硬猜，要么切早了把一句话劈成两半，要么等太久让用户干等。
- 有了它：能拿到"说话开始/结束"的事件，可以做自动断句，也可以做"静音就不发"。

**Silero VAD 是什么**
- 俄罗斯 Silero 团队开源的**小型神经网络** VAD 模型，权重只有不到 2MB，专门为端侧（浏览器/手机）优化。
- **为什么不用更简单的方案**：最朴素的 VAD 是"能量阈值"——音量超过某个值就算有人说话。它在安静的会议室能用，但遇到空调声、键盘声、翻页声就疯了（一直判有人说）；说话小声时又判成没人说。Silero 是**训练出来的**，能区分"人声"和"非人声噪声"的频谱特征，鲁棒性高一个量级。这就是"为什么选它"。

**onnxruntime-web 与 WASM 是什么**
- **ONNX** 是模型的通用交换格式（比喻：模型的 PDF，谁都能打开）。**onnxruntime-web** 是微软官方的推理引擎 JS 版，让浏览器能直接跑 `.onnx` 模型。
- **WASM（WebAssembly）** 是一种浏览器能执行的**二进制字节码**，速度接近原生 C++，远快于 JS。比喻：JS 是"逐句翻译"，WASM 是"直接放母语录音"。
- 两者合起来的意思：**VAD 模型完全跑在用户浏览器本地**，音频不出本机就能判断说话起止，不消耗服务端算力、不增加上传流量。
- 代价：模型文件（`silero_vad.onnx` 等）和 WASM 运行时都要从网络下载，首次几 MB；且**强依赖 CDN**（见下面的坑）。

**本项目怎么用 `@ricky0123/vad-web`**
1. 引入方式是两个全局 `<script>`，`frontend/index.html:9-11`：
   ```html
   <script src="https://cdn.jsdelivr.net/npm/onnxruntime-web@1.22.0/dist/ort.wasm.min.js"></script>
   <script src="https://cdn.jsdelivr.net/npm/@ricky0123/vad-web@0.0.29/dist/bundle.min.js"></script>
   ```
   注意是 `<script>` 标签全局挂载，**没有走 npm import**——`frontend/package.json` 里根本没有 `@ricky0123/vad-web` 这个依赖。
2. 类型声明在 `frontend/src/components/AudioRecorder.tsx:6-18`，手写了一个 `declare global { interface Window { vad: {...} } }`，因为它是全局变量、TS 不认识它。
3. 创建与启动：`AudioRecorder.tsx:170-186`
   ```ts
   const vadInstance = await window.vad.MicVAD.new({
     getStream: async () => stream,   // 复用 getUserMedia 拿到的同一条流，不再要一次麦克风
     onnxWASMBasePath: 'https://cdn.jsdelivr.net/npm/onnxruntime-web@1.22.0/dist/',
     baseAssetPath: 'https://cdn.jsdelivr.net/npm/@ricky0123/vad-web@0.0.29/dist/',
     onSpeechStart: () => { if (mountedRef.current) onSpeechStart?.(); },
     onSpeechEnd:   () => { if (mountedRef.current) onSpeechEnd?.(); },
   });
   vadRef.current = vadInstance;
   await vadInstance.start();
   ```
   `getStream` 传的是同一个 `MediaStream`（:171），避免向浏览器要两次麦克风权限。回调触发时先查 `mountedRef.current`（:175/:180），防止组件卸载后调状态。
   - 顺带记一个细节：`MicVAD.new` 里**只传了上面这些参数**，没传 `threshold`（判为人声的概率门限）、`minSpeechMs`（最短语音时长）、`redemptionMs`（短暂静音多久算同一个人还在说）这类调参项，**全用库默认值**。默认值具体是多少【未能核实】——它们封在 `bundle.min.js` 里，仓库中看不到。
4. **必须说清的真相**：VAD 目前**没有参与任何业务决策**。`onSpeechStart/onSpeechEnd` 一路传到 `frontend/src/pages/VoiceInterviewPage.tsx:870-876` 的 `handleSpeechStart`/`handleSpeechEnd`，而这两个函数在 `:654-655` 是**空函数体**。真正拦掉"AI 说话期间麦克风数据"的是 `VoiceInterviewPage.tsx:641` 的 `isAiSpeakingRef.current || isSubmittingRef.current`，跟 VAD 无关。所以准确表述是：**Silero VAD 已接入并启动，但回调还没接线，是"装了没通电"的组件**；断句目前完全靠服务端 `server_vad`（见 2.12）。自曝这一点比被面试官问出来强。
5. 代价：多两个 CDN 依赖（jsdelivr），首屏多下载 WASM 运行时 + 模型；国内网络下 CDN 不稳会直接导致 `window.vad` 未定义，代码只能抛 `'VAD library not loaded. Please refresh the page.'`（`AudioRecorder.tsx:166-168`）然后就整条采集链起不来——**VAD 挂了会连累录音**（因为 `MicVAD.new` 失败就走 catch，:263-272），这是个真实的耦合风险。

**前端 VAD 和 2.12 的 server_vad，到底谁在断句？**
1. 服务端 `server_vad`（跑在阿里云那一侧）＝**真正在干活的那个**：它听完整条音频流，按静音时长判句尾，定稿后回调 `onFinal`。
2. 前端 Silero VAD＝**装了但没通电**：`onSpeechStart/onSpeechEnd` 一路传到 `VoiceInterviewPage.tsx:654-655`，而那里是空函数体，不参与任何判断。
3. 那它为什么还留在代码里？因为它能解决服务端**天然做不到**的两件事：① 静音段干脆不发音频（服务端必须先收到音频才知道是静音）；② 采集侧就知道"人在不在说"。现状是第 ① 条没接上——AI 说话期间的数据是靠 `isAiSpeakingRef` 门控丢的（`VoiceInterviewPage.tsx:641`），跟 VAD 无关。
4. 面试话术：**不要说"我们用 VAD 断句"**（断句是服务端 server_vad 的功劳）。要说"前端集成了 Silero + onnxruntime-web 做本地语音活动检测，能拿到说话起止事件；目前这两个回调还没接业务逻辑，断句由服务端 server_vad 负责"。既准确，又顺势展示了你知道缺什么。

**⚠️ npm 1.24.3 与 CDN 1.22.0 不一致这个坑（已核实）**
- `frontend/package.json:17` 的 dependencies 里写着 `"onnxruntime-web": "1.24.3"`。
- 但 `frontend/index.html:9` 从 CDN 加载的是 `onnxruntime-web@1.22.0`，`AudioRecorder.tsx:172` 的 `onnxWASMBasePath` 又硬编码了 `1.22.0/dist/`。
- 结论：**运行时真正用的是 CDN 的 1.22.0；npm 装的那份 1.24.3 是死依赖**，从头到尾没被引用过。三重版本号（1.24.3 / 1.22.0 / 1.22.0）写在同一套代码里。
- 危害：① 本地装的和实际跑的不是一个版本，升级依赖时毫无效果，排查问题会被误导；② 离线环境或 CDN 被墙时 VAD 直接不可用；③ 版本漂移无人察觉。
- 修法：把 `ort.wasm.min.js` 和 vad-web 的资源通过 Vite 打进 bundle（`vite-plugin-wasm` 已经在 `package.json` 的 devDependencies 里了），或至少把 `onnxWASMBasePath` 指向本地 `public/` 目录，并删掉那个死依赖。

### 2.12 DashScope Qwen3 实时语音：ASR / TTS / 流式

**先扫盲三个名词**
- **ASR**：Automatic Speech Recognition，自动语音识别，**语音 → 文字**。比喻：速记员。本项目用的是阿里云百炼 `qwen3-asr-flash-realtime`（`application.yml:232`）。
- **TTS**：Text To Speech，**文字 → 语音**。比喻：播音员。本项目用的是 `qwen3-tts-flash-realtime`（`application.yml:246`）。
- **实时/流式 vs 一次性合成**：一次性（离线）合成＝"句子给我，我等它整段说完了再还你一整个音频文件"；实时/流式＝"我一边生成一边把音频片段推给你，你也一边播"。比喻：一次性是等整张专辑录完再发货，流式是边唱边直播。语音面试里**用户等多 1 秒就明显觉得"这 AI 好卡"**，所以必须流式。

**ASR 侧：server_vad 服务端断句**
- **是什么**：`server_vad`＝把"判断用户说完了没有"这件事交给服务端模型做（"服务端"指阿里云那边，不是我们的服务器）。术语首现解释：VAD = 语音活动检测（见 2.11）。
- **解决什么问题**：谁说完了这件事，客户端自己猜很容易错——用户中途思考停顿 1 秒，客户端就以为说完了，一句话被劈成两段，AI 会答非所问。
- **本项目怎么用**：`application.yml:237-241`
  ```yaml
  enable-turn-detection: true
  turn-detection-type: server_vad
  turn-detection-threshold: 0.0
  # 静音多久判为一句结束；中文面试思考停顿常见 2-3s，设 2000 避免句中切段
  turn-detection-silence-duration-ms: ${APP_VOICE_ASR_SILENCE_MS:2000}
  ```
  **2000ms** 是本项目当前的正式值（`turn-detection-silence-duration-ms: 2000`）。它透传到 SDK：`QwenAsrService.java:282-289` 的 `OmniRealtimeConfig.builder().turnDetectionType(...).turnDetectionSilenceDurationMs(...)`。
- **代价**：2 秒静音才断句意味着**用户说完后要干等 2 秒**才看到 AI 反应，体验变钝；设小又容易切碎句子。这是个必须双方权衡的旋钮，**2000 是为中文面试的思考停顿特意调大的**。
- **文档漂移警告**：架构文档写 `turn-detection-silence-duration-ms: 400`，`QwenAsrService.java:36` 的 javadoc 也还写着 "Server-side VAD with 400ms silence duration"——**都是过时注释**，源码实际是 2000ms。旧稿里"ASR 断句延迟 800ms → 400ms（-50%）"这个指标也是按 400ms 口径记的，现在配置已经改了，引用时要说清"文档记录的历史自测值"。

**ASR 侧：本项目怎么收发**
1. 建连：`QwenAsrService.startTranscription`（:140-167，有 onFinal/onPartial/onReady/onError 四个回调）→ 内部 `startTranscriptionLocked`（:216-325）。
2. 关键顺序：先把 session 塞进 map（:269），**再**用一个独立线程 `"ASR-Connection-"+sessionId`（:272-316）去做阻塞的 `conversation.connect()`；`updateSession` 成功后才 `markReady()` + 触发 `onReady`（:297-300）。这样 `hasActiveSession` 立刻为 true，音频不会因为建连慢被丢。
3. 推音频：`sendAudio(sessionId, byte[])`（:340-369）——先 `awaitReady(1200)` 等最多 1.2 秒（:347），再 base64 后 `appendAudio`（:357-360）。失败一律抛 `IllegalStateException("ASR append failed: " + sessionId)`（:367），**故意不在这里调 onError**（:366 的注释写了原因：避免用户先看到红条再自动恢复）。
4. 收结果：`handleServerEvent`（:461-534）认三类事件——`conversation.item.input_audio_transcription.completed` 是**定稿**（:481-494，还带回 language/emotion）→ `onFinal`；`.text` / `.delta` 是**中间态**（:496-499）→ `dispatchPartialTranscript` → `onPartial`（用于实时字幕，:539-551）；`error` → `onError`。中间态的文本要从 `text` + `stash` 两段拼（:568-581，`stash` 是还没确认的草稿尾巴）。
5. 重连：`restartTranscription`（:172-214）= stop → `Thread.sleep(200)`（:190）→ start → 轮询 10 次 × 100ms 验证是否 ready（:197-212）。上层还有一层保险：`VoiceInterviewWebSocketHandler.java:437-454` 的 `checkAsrReadyOrRetry`，每 10 秒（`ASR_READY_CHECK_DELAY_SECONDS`，:91）检查一次，最多重试 2 次（`MAX_ASR_READY_RETRY`，:90）。
6. 一个真实踩过的坑写在代码注释里：`QwenAsrService.java:253` —— `onClose` 里只移除"和本次连接相同"的 session，否则重连后旧连接的 onClose 会误删新连接，症状是**"第三轮起无声"**。

**TTS 侧：音色 Cherry、commit 模式、24kHz**
- **本项目怎么用**：`application.yml:245-254`
  ```yaml
  model: qwen3-tts-flash-realtime
  voice: Cherry            # 音色
  format: pcm
  sample-rate: 24000
  mode: commit
  language-type: Chinese
  speech-rate: 1.0
  volume: 60
  ```
  `voice: Cherry` 是阿里云内置音色名（音色列表见 `:244` 注释的官方文档链接）。**注意这里有个容易说错的点**：`application.yml:226` 还有另一个配置 `app.voice-interview.tts.default-voice: siyue`（思悦，温柔自然女声），那是**旧的、给非实时 TTS 路径用的**；Qwen3 实时链路上真正生效的是 `qwen.tts.voice: Cherry`（:248）。面试时说"实时 TTS 用 Cherry"是对的，说"`default-voice` 是 Cherry"是错的。
- `mode: commit`＝手动提交模式：先 `appendText` 文本，再显式 `commit()` 告诉服务端"我说完了，开始合成"（`QwenTtsService.java:186-187`）。好处是可以多段文本累积后一次性合成。
- **代码与配置不一致（真实缺陷）**：`QwenTtsService.java:238-241` 的 `getAudioFormat()` **硬编码返回 `PCM_24000HZ_MONO_16BIT`**，而配置里的 `sample-rate`（`applyTtsConfig`，:79）只是被存进字段、**从未参与格式选择**。所以 `sample-rate: 24000` 是个**死配置**——它恰好和硬编码值一样才没出事，改小改大都不会生效。被追问"配置怎么生效的"要能坦白这一点。
- **每次合成新建一条 WebSocket**：`synthesize()`（:115-230）每次都 `new QwenTtsRealtime(...)`（:163）→ `connect()`（:167，阻塞）→ 合成 → `finally` 里 `close()`（:213-219）。一句话一条连接，没有连接池。代价：每句都有握手成本、且连接数随并发线性增长（`max-concurrent-tts-per-session: 3` 就是用来压这个的）。

**TTS 单次合成 500 字符上限**
- **它是什么**：云厂商对"一次 TTS 请求能塞多长文本"的限制，超了会报参数错误或被服务端截断。
- **本项目的情况**：`app/src/main/java/interview/guide/modules/voiceinterview/` 全目录搜索，**找不到任何 500 字符的校验或截断逻辑**（唯一命中 `500` 的是 `VoiceInterviewSessionEntity.java:103` 的 `evaluate_error` 字段长度）。本项目自己真正生效的上限是 `ai-question-max-chars: 120`（`application.yml:265`），实现在 `DashscopeLlmService.java:199-223` 的 `optimizeForVoice()`：超过上限就 `substring(0, maxChars)`，然后在**句子终止标点**处回退（:210-220，若最近标点在 `maxChars/2` 之后就在那儿断句，否则加省略号）。
- **结论**：**"500 字符上限"这个数字在仓库里无法核实**【未能核实】——它只出现在旧架构文档里，很可能是从阿里云官方产品文档抄来的服务侧限制。
- 背的时候可以说："服务端对单次输入有长度限制（文档记 500 字符），但本项目从没碰到过，因为我们自己把单轮回复卡在了 120 字符。" **不要把它说成代码里的常量**，代码里没有这个数。

**首包延迟：为什么它决定体感**
- **是什么**：从"用户说完最后一个字"到"用户听到 AI 第一个音"的时间。比喻：不是问厨师做完这顿饭要多久，而是问"多久能端上第一道菜"。
- **解决什么问题**：AI 回答一共 3 秒 vs 5 秒，用户其实不太有感；但首包是 0.5 秒还是 2.5 秒，感受是天壤之别。**体感 = 首包，不是总时长**。这是语音产品最反直觉的一条。
- **本项目怎么用**（三处埋点，可指）：
  - 首 token：`VoiceInterviewWebSocketHandler.java:666-672`，用 `firstTokenAtNanos.compareAndSet(0L, ...)` 保证只记一次，指标名 `app.voice.interview.llm.first_token_latency`
  - 整体 LLM：`app.voice.interview.llm.duration`（:697）
  - TTS 阶段：`app.voice.interview.tts.duration`（:715）
- **优化手段（这就是流式存在的理由）**：不用流式时，链路是**串行**的——等 LLM 把整段话生成完（可能 3~5 秒）→ 再等 TTS 把整段合成完（又 1~2 秒）→ 才发出第一个音频包。用户听到第一个字要等 5 秒以上。
- 本项目改成**边生成边切句边合成**（详见下一段"一轮对话的完整链路"），首包只等于"第一句话生成完 + 第一句话合成完"。
- 开场白还专门做了**预热缓存**：`@PostConstruct warmupOpeningAudioCache()`（`VoiceInterviewWebSocketHandler.java:108-130`）在应用启动时就把所有开场白模板（`skillQuestions` 各方向 + 算法题 + 后端题，:116-121）提前合成好塞进 `openingAudioCache`，用户一进来直接命中缓存，**首包延迟约等于 0**。
- **代价**：预热会占用启动时间和 TTS 调用配额；缓存以文本为 key（:138），文本模板一改缓存全失效。

**一轮对话的完整链路（句子级并发 TTS，1→8）**
1. LLM 流式吐 token：`DashscopeLlmService.chatStreamSentences(...)`（`app/.../service/DashscopeLlmService.java:69-152`），一边把 token 推给前端做实时字幕（`onToken` → `sendTextMessage(session, partialText, false)`，`VoiceInterviewWebSocketHandler.java:673`），一边做**句子切分**。
2. 切句靠标点：`hasTerminalSince(token)`（`DashscopeLlmService.java:238-245`）检查新 token 里有没有终止标点（`TERMINAL_PUNCTUATION`）；一有就把 `lastSentenceEnd` 到当前位置的文本整段回调出去（:99-107），句尾残余在流结束时补发（:133-140）。
3. 每句立刻进 TTS：`sentence -> chunkEmitter.submit(sentence)`（`VoiceInterviewWebSocketHandler.java:675-681`）。
4. **并发闸门**：`Semaphore`，许可数 `max-concurrent-tts-per-session: 3`（`application.yml:271` → `VoiceInterviewProperties.java:45` → `VoiceInterviewWebSocketHandler.java:651-652` 的 `new Semaphore(Math.max(1, ...))`）。
5. 每句一个异步任务调 `ttsService.synthesize(sentence)`，`finally` 里 release 许可（:1003-1010）。
6. **保序**：`OrderedTtsChunkEmitter`（:976-1091）用 `ConcurrentHashMap<Integer, future>` + `AtomicInteger nextIndex` 按下标严格顺序 drain（:1041-1078），谁先合成完不重要，**必须按 0、1、2 的顺序播**，否则 AI 说的话会前后颠倒。
7. 单句超时：`long ttsTimeoutSec = Math.max(5, getTtsTimeoutSeconds())`（:654 → 配置 `tts-timeout-seconds: 8`，`application.yml:269`），每句 `future.get(ttsTimeoutSec, SECONDS)`（:737、:1055）。**注意是双层超时**：外层业务 8 秒，`QwenTtsService.java:192` 内层还有 `synthesisLatch.await(30, SECONDS)` 兜底。整体 drain 的超时是动态算的：`Math.max(ttsTimeoutSec + 2, (ttsTimeoutSec + 1) * max(1, 已提交句子数))`（:1026）。
8. 下发与播放：每句 PCM 用 `convertPcmToWav(pcm)` 加 WAV 头后以 `{type:'audio_chunk', data, index, isLast}` 推给前端（:1057）；前端 `VoiceInterviewPage.tsx:221-254` 解码时**直接跳过 44 字节 WAV 头**（`pcmOffset = 44`，:230），转成 float32（`/32768.0`，:234），塞进 24kHz 的 `AudioBuffer` 排队顺序播（:238-244）。
- **兜底（必须知道）**：如果一句都没合成出来（`emittedChunks == 0`），会用**完整文本**再合成一次当兜底（`VoiceInterviewWebSocketHandler.java:716-727`）；非分片模式下则是所有句子失败才兜底（:756-771）。所以"某一句 TTS 挂了"不会让整轮没声音。
- **播放看门狗**：前端按 WAV 头算音频时长，多等 1.5 秒就强制收尾（`VoiceInterviewPage.tsx:150-154`，解析失败兜底 15 秒），分片模式另有 30 秒 drain 上限（:199、:212）。

**为什么从阿里云 NLS 迁到 Qwen3 实时模型**
以下口径来自项目文档记录的自测对比（不是我在这次核对中重新跑出来的）：ASR 准确率 ~90% → 95%+；ASR 断句延迟 ~800ms → ~400ms（-50%，注意这个 400ms 对应旧配置，现已改成 2000ms，见前文漂移警告）；TTS 首包 ~500ms → ~200ms（-60%）；**环境变量 9 个 → 2 个**。
- **迁移的真实理由**（这才是面试要答的）：① NLS 那套要维护一堆独立参数（AppKey、Token、多个环境变量，早期 9 个），Qwen3 实时统一成**一个 API Key**——`AI_BAILIAN_API_KEY`（`application.yml:233` 和 `:247` 指向同一个变量）；② NLS 是"老一代"语音产品线，Qwen3 Realtime 走的是新的 WebSocket 双向流协议，**原生带回环检测（turn detection）、原生流式 partial 字幕**，不用自己拼；③ 与项目其它 AI 能力（`qwen3.5-flash`、`text-embedding-v3`）**同一套百炼账号、同一套账单和限流**，运维面收窄。
- **代价**：**厂商锁定（vendor lock-in）**。ASR 和 TTS 都绑死在 DashScope 上；而且代码里用的是 dashscope SDK 的 `OmniRealtimeConversation` / `QwenTtsRealtime` 这类专有类（`QwenAsrService.java:3-8`、`QwenTtsService.java:3-7`），换厂商等于重写这两个 Service。另外错误提示文案里还残留着过时的变量名：`VoiceInterviewWebSocketHandler.java:846-864` 在 403 时会让用户"检查 `ALIYUN_ACCESS_KEY`"，那个变量**早就废弃了**（现在只有 `AI_BAILIAN_API_KEY`），属于文案漂移，也是可以主动自曝的一条。
