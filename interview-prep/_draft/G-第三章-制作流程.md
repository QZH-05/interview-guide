## 三、项目完整制作流程（需求 → 架构 → 编码 → 测试 → 上线）

> **这一章的作用**：面试官问"这个项目你是怎么一步步做出来的"，其实是在考**工程判断力**——你到底是有计划地推进，还是随手堆功能。
> **讲法**：先说下面这张总览表（10 秒），然后**挑一个阶段深入讲**，千万别五个阶段平铺直叙。

### 3.0 五阶段总览（先给这张表，再挑着展开）

| 阶段 | 这一阶段要解决什么问题 | 核心产出 | 最关键的一个决策 |
|---|---|---|---|
| 一、需求分析 | 做什么、**不做什么** | 主链路闭环清单 + 3 项"明确不做" | 先做闭环（简历→出题→评估），不堆单点功能 |
| 二、架构设计 | 代码怎么分层、错误怎么传、服务怎么起 | 分层规范（`AGENTS.md`）+ 10 域错误码 + docker-compose 拓扑 | 工程约束写成强制清单，而不是靠自觉 |
| 三、编码实现 | 按什么顺序写、AI 层怎么抽象 | 6 个业务模块 + `common/ai` 抽象层 | 语音不走 Spring AI，直接对接原生实时 SDK |
| 四、测试 | 哪些该测、哪些不测 | 21 个测试类 / 195 个方法 | 测试预算优先投给"纯逻辑、边界多"的部分 |
| 五、上线运维 | 怎么让别人一键跑起来 | Dockerfile ×2 + compose ×2 + nginx 反代 | 镜像构建只打包，测试不进构建流程 |

### 阶段一 · 需求分析（产出：功能闭环清单 + 明确的"不做什么"）

**这一阶段解决的问题**：一个人做一个 9 个月的项目，最大的风险不是技术难，而是**什么都想做、最后什么都做不完**。所以需求阶段我做的其实是"砍需求"。

**我做的事**：把"求职者练面试"这件事拆成一条主链路，再决定哪些是必须有的、哪些可以后置。

**核心产出：主链路闭环**
```
上传简历 → 解析打分 → 生成针对性题目 → 面试（文字/语音）→ 多维度评估报告 → 复盘
```

**关键决策 1：先做闭环，不做单点功能**
> 很多同类项目会先堆"题库"或先做漂亮的对话界面，但用户真正要的是"练完有反馈"。**没有评估环节，出题再准也没用**，所以我先把"简历→出题→评估"跑通，哪怕早期题目质量一般。

**关键决策 2：明确写下"不做什么"**
> 项目 README 的 TODO 里我刻意留了三项没做：`打通模拟面试和知识库`（让面试官能针对你的知识库提问）、`语音接入 WebRTC`、`支持更多 TTS 音色`。
> **为什么不顺手做**：前两项各自是独立的大改造（一个要重做检索注入链路，一个要动传输层），第三项是纯体验优化。在核心链路还没稳的时候做这些，会让"每个功能都半成品"。**面试里能说出"我判断什么不做"，比多列一个功能更有说服力。**

**关键决策 3：拆出独立的知识库 RAG 模块**
> 我最初想的是"面试官直接读你上传的文档提问"，但推演后发现这会让出题链路变成两套逻辑。最后拆成**独立的知识库问答模块**，让面试官用 Skill 岗位手册、让知识库用 RAG——**职责不混，各自可独立优化**（理由详见第四章 4.1）。

### 阶段二 · 架构设计（产出：分层规范 + 错误码体系 + 部署拓扑）

**这一阶段解决的问题**：一个人写 1.9 万行代码，**如果没有一条"机器和人都不用商量的规则"，三个月后自己都不认识自己的代码**。所以我把约束写成了文件。

**核心产出 1：单模块 Gradle + 按功能分包**
> 没有用多模块（`common`/`infrastructure`/`modules` 三个包已经够表达边界），理由：**多模块 Gradle 的构建复杂度和 IDE 索引成本，对一个单人项目是纯负债**。包级划分同样能强制依赖方向（`modules` 可以依赖 `common`/`infrastructure`，反过来不行）。

**核心产出 2：一份写进 `AGENTS.md` 的强制规范**（这份文件是真实存在的，10 KB，面试可以主动提）
> `AGENTS.md` 是我给"后续参与项目的人（以及 AI 编码助手）"定的工程宪法。关键几条，**每条都要能说出"为什么"**：
> - **禁止** `throw new RuntimeException()`，所有业务异常走 `BusinessException(ErrorCode.XXX, msg)`，全局异常处理器统一返回 **HTTP 200 + `Result.error(code, message)`**
>   - **为什么 HTTP 200**：前端只需要一套解包逻辑（判断 `code`），不用同时处理"网络层失败"和"业务层失败"两种分支。
> - **禁止** 直接返回 Entity 给前端，必须转 DTO（MapStruct 编译期生成转换代码）
>   - **为什么**：Entity 字段一变就泄漏数据库结构，而且惰性加载的关联字段会直接把序列化搞崩。
> - **禁止** 在 `@Transactional` 方法内调用外部 API（LLM、S3）
>   - **为什么**：**网络 IO 会一直占着数据库连接**，这是连接池被打满最常见的原因。LLM 一次调用几秒到几十秒，事务持有连接几十秒，并发一上来就全卡住。
> - **禁止** 同类内部调用 `@Transactional` 方法
>   - **为什么**：Spring 事务是 AOP 代理实现的，`this.method()` 走的是原始对象、**不经过代理，事务静默失效**——不报错，但回滚不生效，最难查的一类 bug。
> - **禁止** `@Value` 散落在 Service，配置集中到 `@ConfigurationProperties`
>   - **为什么**：散落的 `@Value` 没法做类型校验、没法集中看到配置全貌、改个名字要全局搜字符串。
> - **禁止** `Executors.newXxxThreadPool()`（无界队列 OOM 风险），必须用 `ThreadPoolExecutor` 显式指定参数
>   - **为什么**：`newFixedThreadPool` 的队列是无界的，任务堆积时内存一直涨直到 OOM，而 `ThreadPoolExecutor` 强制你面对"队列满了怎么办"。

**关键决策：错误码按业务域分段（1xxx 通用 / 2xxx 简历 / 3xxx 面试 / 4xxx 存储 / 5xxx 导出 / 6xxx 知识库 / 7xxx AI / 8xxx 限流 / 9xxx 日程 / 10xxx 语音）**
> 理由很实际：**HTTP 状态码不够用**。光是"参数错"就有几十种业务含义，全用一个 400 前端没法区分。分域编码让前端能精确判断"这次该提示用户重试、还是该让他改输入"。AI 场景尤其需要——`7002 AI_SERVICE_TIMEOUT` 和 `3006 出题失败` 对用户是两种完全不同的引导（一个是"稍后再试"，一个是"检查你的简历内容"）。

**核心产出 3：部署拓扑**
> 用一份 `docker-compose.yml` 起 6 个服务：`postgres`（pgvector 镜像）/ `redis` / `minio`（对象存储）/ `createbuckets`（一次性任务，自动建桶）/ `app` / `frontend`。
> **关键决策：用 `healthcheck` + `depends_on: service_healthy` 保证启动顺序**，而不是靠 `depends_on` 的"容器启动了"。**这是踩过坑的**——数据库容器"启动了"和"能接受连接了"是两回事，早期版本 app 会因为 PG 还没 ready 而启动失败；现在 postgres/redis/minio 都有健康检查，`app` 等它们健康后才起。

### 阶段三 · 编码实现（产出：6 个业务模块 + AI 抽象层）

**这一阶段解决的问题**：AI 应用的代码最容易写成"到处都在 new 一个模型客户端、到处都在拼 prompt"，我要的是**所有 LLM 调用只有一个入口**。

按我实际的实现顺序，分五步：

| 步骤 | 产出 | 关键决策与理由 |
|---|---|---|
| 1. 主链路 | 简历上传解析 → 出题 → 文字面试 → 评估报告 | 先把业务闭环跑通，AI 只用最基本的 prompt 调用 |
| 2. Skill 化 | `resources/skills/` 10 个方向目录 + 19 份共享参考资料 | **把面试官人设从 prompt 字符串里抽出来变成"文件 + 元数据"**。理由：改人设不用改代码、不用重训、不用重启；新增方向 = 新增目录（详见第四章 4.1） |
| 3. 语音链路 | `VoiceInterviewWebSocketHandler` 主循环 + ASR/TTS 会话管理 | **决策：语音不用 Spring AI，直接用 DashScope 原生 SDK**。理由：实时语音是双向流式协议，Spring AI 的 ChatClient 抽象覆盖不到；**架构上分层，而不是硬套框架**（详见第四章 4.3） |
| 4. 多 Provider | `LlmProviderRegistry` + 设置页 + DB 加密持久化 | **决策：Provider 配置存数据库、API Key 用 AES-256-GCM 加密、按 providerId 缓存 ChatClient**。理由：换模型是运营动作，不该改配置文件重启服务 |
| 5. 评估统一 | `UnifiedEvaluationService` 文本/语音共用 | **决策：把评估从两个模块抽成一个共用引擎**。理由：文本和语音的评估 rubric、分批逻辑、汇总逻辑完全一样，**差别只在"输入从哪来"**——这是典型的过早分裂，我后来合并了 |

**编码期最大的一个坑（值得主动讲）**
> `spring-ai-agent-utils` 的 SkillsTool 我一开始以为它靠 `SKILL.md` 里的 `# Additional Resources` 段落去加载参考文件。后来发现**那段只是给模型看的说明文字，后端真正加载哪个文件完全按 `skill.meta.yml` 的 `ref` / `shared` 字段走**。这导致我有一次改了 SKILL.md 里的引用路径但没改 meta.yml，模型拿到的参考资料和文档描述不一致。
> **教训是：任何"看起来像配置又像文档"的双份信息，最终一定会不一致。** 后来我给 Skill 目录加了一条自检：两个文件里出现的类目名必须能对上。

### 阶段四 · 测试（产出：21 个测试类 / 195 个测试方法）

**这一阶段解决的问题**：哪些代码值得写测试？我的判断标准是**"这段逻辑是不是纯的、边界是不是多、错了会不会很难查"**。

**我做的事**
> 技术栈是 JUnit 5 + Mockito + AssertJ，测试方法用**中文 `@DisplayName`** 描述意图（因为测试的名称是给人看的，写英文我半年后也要猜），按功能用 `@Nested` 分组。集成测试用 **H2 内存数据库**（`ddl-auto: create-drop`），因为测试不该依赖外部 PostgreSQL。

**覆盖重点与理由**
> 覆盖最厚的是这几类：**文档解析**（Tika 对 PDF/DOCX/TXT 的各种脏数据，13 + 8 个用例）、**文本清洗**（24 个，边界最多）、**知识库向量服务**（23 个）、**Provider 配置服务**（21 个）、以及**限流 Lua 脚本的单元测试**。
> 理由：这些都是**纯逻辑、边界多、容易写错、且不需要真实外部依赖**的部分。把测试预算花在"能稳定复现的纯函数"上，投入产出比最高。

**必须主动承认的现实（这是真实技术债，不是谦虚）**
> 我的测试分布是不均衡的：**`resume`、`interview`（出题与评估，业务最核心的部分）、`interviewschedule` 这三个模块目前没有自动化测试**，`PdfExportService` 同样零测试；全项目只有一个 `@SpringBootTest` 集成测试类，而且它当前是 `@Disabled` 的；另外还有若干测试被 `@Disabled` 跳过（注解 9 处，其中 4 处是类级注解、会禁掉整类，**按方法数约 48 个**——这个口径我自己也要再数一遍，面试时说"**有一部分被禁用**"比报一个精确数字更安全）。
> **为什么会这样**：出题和评估的断言很难写——输出是自然语言 + 分数，没有稳定的期望值；我当时的替代手段是**把不确定性用工程手段约束掉**（固定 rubric、温度 0.2、算数交给代码、结构校验），让它"错也错得可控"。
> **如果重做我会怎么做**：给 LLM 调用做一层可录制的桩（把真实响应录下来做回归基准），断言"结构 + 分数区间 + 关键字段"，而不是断言精确文本。这样既稳定又能挡住大部分回归。

### 阶段五 · 上线运维（产出：一键部署 + 镜像构建 + 反向代理）

**这一阶段解决的问题**：**让别人能跑起来**。个人项目最容易死在"只有作者的机器能跑"。

**核心产出**
> `docker-compose.yml`（生产形态：MinIO 做对象存储）、`docker-compose.dev.yml`（只起基础设施，应用在 IDE 里跑，方便调试）、`app/Dockerfile`（多阶段构建：`gradle:8.14-jdk21` 编译 → `eclipse-temurin:21-jre` 运行）、`frontend/Dockerfile`（`node:20-alpine` 构建 → `nginx:alpine` 托管）、`nginx.conf`（SPA fallback + `/api/` 反代到 app）。

**关键决策 1：多阶段构建 + 依赖预热**
> Dockerfile 里先跑一次 `gradle dependencies` 把依赖层缓存下来再做正式编译。**因为 Docker 是分层缓存的，依赖没变时这一层会命中缓存**，镜像重建从几分钟降到几十秒。

**关键决策 2：开发环境用 RustFS 而不是 MinIO**
> `docker-compose.dev.yml` 里我换成了 RustFS（Rust 写的 S3 兼容存储）——**本机开发只关心接口兼容，轻量更省资源**；生产走 MinIO。代价是**桶要手动在控制台建**，这个体验不好，是个待改的点。

**关键决策 3：镜像构建时跳过测试（`-x test`）**
> 理由：镜像构建应该只负责"打包"，测试应该在 CI 里跑、跑失败了就不该走到构建这一步。**（诚实补充：这个项目目前还没有 CI 流水线，测试是我本地手动跑的——这是我计划补的第一件事。`-x test` 在没有 CI 的阶段其实是**风险**，因为等于没人拦你。）**

**上线期发现并记录的真实缺口（强烈建议主动讲这个）**
> 我复查 `frontend/nginx.conf` 时发现一个**部署级缺陷**：配置里只有 SPA fallback 和 `/api/` 的反代，**没有 `/ws/` 的 location，也没有 `proxy_set_header Upgrade / Connection`**。
> 后果是：**语音面试的 WebSocket 在容器化部署后不会被代理到后端**，只有本机直连 `ws://localhost:8080` 才通；文档里写的"Nginx 支持 WebSocket 代理"是**目标状态，不是当前状态**。
> 修法很简单（加一个带 Upgrade 头的 `/ws/` location），我把它记下来是因为**这类问题最危险的地方在于"开发环境永远正常"**——我用的是 Vite 直连后端，直到我真正去读 nginx.conf 才发现。**这就是为什么部署配置也需要 code review。**
