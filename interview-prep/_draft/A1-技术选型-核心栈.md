### 2.1 Java 21（含虚拟线程）

**① 它是什么**
Java 21 是 LTS 长期支持版 JDK。它最出圈的礼物叫**虚拟线程**（Virtual Thread，JDK 21 正式转正）。
虚拟线程不是操作系统线程，是 JVM 自己调度的"轻量线程"。一个 OS 线程能同时带成千上万个虚拟线程。
生活化比喻：老式银行是"一个客户配一个柜员，客户在填单子柜员就干看着"；虚拟线程是"呼叫中心"——你在等对方查资料（I/O 等待）时，接线员立刻挂起你这通、去接下一通，回来再续上。

**② 它解决什么问题**
Java 传统线程（平台线程）是 1:1 绑 OS 线程，一个约 1MB 栈。Tomcat 默认 200 个工作线程。
本项目的接口动不动要调 LLM：出题、评分、生成报告，一次几秒到几十秒。
没有虚拟线程会怎样：第 201 个请求开始在队列里干等，用户看到白屏；把线程池调到 2000 又直接 OOM。
痛点一句话：**阻塞在 I/O 上的线程白占内存**。

**③ 本项目怎么用它**
1. 全局开关，让 Tomcat 每个请求跑在虚拟线程上：
   ```yaml
   # app/src/main/resources/application.yml:36-38
   threads:
     virtual:
       enabled: true
   ```
   上面两行注释（`app/src/main/resources/application.yml:34-35`）写的就是理由："显著提升 I/O 密集型场景的并发能力，特别适合 AI 调用和 SSE 长连接"。
2. 自己写的执行器也用虚拟线程：
   - `app/src/main/java/interview/guide/modules/interview/service/InterviewQuestionService.java:102` → `this.questionExecutor = Executors.newVirtualThreadPerTaskExecutor();`
     用来并行出题：简历题、方向题两个 `CompletableFuture` 各跑一个虚拟线程（`InterviewQuestionService.java:148-156`）。
   - `app/src/main/java/interview/guide/modules/voiceinterview/handler/VoiceInterviewWebSocketHandler.java:75` → 同样一句。
     注释（`VoiceInterviewWebSocketHandler.java:72-74`）说明用途："LLM / TTS / JDBC 等阻塞工作全部跑在虚拟线程上，避免占满 utteranceMergeScheduler 的 2 个调度线程"。
3. 构建与运行环境锁死 21：Gradle toolchain `JavaLanguageVersion.of(21)`（`app/build.gradle:90-94`）；运行镜像 `eclipse-temurin:21-jre`（`app/Dockerfile:44`），构建镜像 `gradle:8.14-jdk21`（`app/Dockerfile:5`）。
4. 顺手用上的其它 Java 21 语法（都是 21 的语言特性，面试常被追问）：
   - `record`：`private record QuestionListDTO(List<QuestionDTO> questions) {}`（`app/src/main/java/interview/guide/modules/interview/service/InterviewQuestionService.java:86-89`）
   - 文本块：`STRICT_JSON_INSTRUCTION`（`app/src/main/java/interview/guide/common/ai/StructuredOutputInvoker.java:22-27`）
   - `switch` 表达式：`calculateIntervalMs`（`app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java:129-135`）
   - `instanceof` 模式匹配：`convertToLong`（`RateLimitAspect.java:139-141`）
   - `SequencedCollection` 的 `getFirst()`：`KnowledgeBaseQueryService.java:180`、`RagChatSessionService.java:270`（21 之前只能 `get(0)`）

机制顺序（从入口到出口）：
1. HTTP 请求进 Tomcat → Tomcat 交给一个虚拟线程执行 Controller。
2. Service 里发起 LLM 调用 → 线程阻塞在 socket 读。
3. JVM 把这个虚拟线程从载体线程（carrier thread）上摘下来（unmount），载体线程去跑别的请求。
4. LLM 响应回来 → JVM 重新挂载（mount），代码从阻塞点继续往下走。
所以"等待"不再占用 OS 线程，机器能扛的并发请求数从"线程池大小"变成"内存 + 下游限流"。

**④ 为什么选它 + 代价**
替代方案一：加大 Tomcat 线程池（`server.tomcat.threads.max=1000`）。问题是每个线程要真金白银的内存，且下游 LLM 本来就有并发限制，排队只是换个地方排。
替代方案二：整站改成 WebFlux 响应式。问题是响应式要求整条链路都是 `Mono/Flux`，而本项目持久层是阻塞的 JPA（`app/src/main/java/interview/guide/App.java` 走的是 MVC），改造成本极高。本项目采取折中：**只让流式接口用 WebFlux**（`KnowledgeBaseController.java:106` 的 `Flux<String>`、`RagChatController.java:116` 的 `Flux<ServerSentEvent<String>>`），其余留给虚拟线程。
本项目自己的短板，得能说出口：
1. Java 21 里虚拟线程遇到 `synchronized` 块会"钉住"（pin）载体线程，失去调度优势。代码里确实有：`app/src/main/java/interview/guide/modules/voiceinterview/service/QwenAsrService.java:104`（`sessionLocks`）、`:106-108`（`lockForSession`）、`:164` 用 `synchronized (lockForSession(sessionId))` 保护 ASR 启停。这个锁只在 ASR 启动/停止/重连时进入，属于低频路径，影响可控，但严格说是个隐患（换成 `ReentrantLock` 就能规避）。
2. 虚拟线程数量暴涨时，压力会原样传给它下游——如果不加限流，会把 LLM 供应商打到 429。所以本项目才必须有 2.8 那套限流。
3. 团队心智负担：`ThreadLocal` 缓存、`synchronized`、`synchronized` 里的阻塞调用都得重新审视。

【未能核实】虚拟线程下这些 `synchronized` 钉住载体线程对语音面试的实际影响（没做过压测对比）。

### 2.2 Spring Boot 4.0.1

**① 它是什么**
Spring Boot 是 Spring 家族的"开箱即用"封装：把 Web、数据库、JSON、日志、配置这些基础设施按默认值自动装配好。
版本号来自 `gradle/libs.versions.toml`：`spring-boot = "4.0.1"`。
生活化比喻：Spring 框架像"自己攒机"（CPU、主板、驱动自己挑自己装），Spring Boot 像"品牌整机"——插电就能用，想换零件再单独换。

**② 它解决什么问题**
没有 Boot 会怎样：你要自己写 `web.xml`、注册 `DispatcherServlet`、配 `DataSource`、配事务管理器、配 Jackson、还要手工对齐几十个 jar 的版本。任何一个版本错配，启动就报 `NoSuchMethodError`。
痛点一句话：**配置和版本对齐是纯粹的内耗**。Boot 用三招解决：starter 依赖聚合、自动配置（`@Conditional` 判断后自动装配）、版本仲裁（BOM 统一管版本）。

**③ 本项目怎么用它**
1. 依赖声明在一个文件里（`app/build.gradle:23-88`），关键几条：
   - `spring-boot-starter-webmvc` —— Boot 4 里 MVC 版 Web 启动器（Boot 3 叫 `spring-boot-starter-web`）
   - `spring-boot-starter-webflux` —— 只用它的 `Flux` 做 RAG 流式返回
   - `spring-boot-starter-data-jpa`、`spring-boot-starter-validation`、`spring-boot-starter-websocket`
   - `runtimeOnly org.postgresql:postgresql`
2. **主动关掉自动配置**，这是本项目最值得讲的一点：
   ```java
   // app/src/main/java/interview/guide/App.java:18-25
   @SpringBootApplication(exclude = {
       OpenAiAudioSpeechAutoConfiguration.class,
       OpenAiAudioTranscriptionAutoConfiguration.class,
       OpenAiChatAutoConfiguration.class,
       OpenAiEmbeddingAutoConfiguration.class,
       OpenAiImageAutoConfiguration.class,
       OpenAiModerationAutoConfiguration.class
   })
   ```
   为什么关：Spring AI 的 OpenAI 自动配置只认 `spring.ai.openai.*` 这一套 key、只造一个 ChatModel；而本项目要支持运行时切换 5 个 Provider（dashscope / lmstudio / kimi / deepseek / glm，`application.yml:106-140`），所以改成自己在 `LlmProviderRegistry` 里按 provider 造 `OpenAiChatModel`（2.3 会展开）。
3. 配置分层：`application.yml` 放默认值，敏感值走环境变量；`@ConfigurationProperties` 承接（`app/src/main/java/interview/guide/common/config/LlmProviderProperties.java:12` → `prefix = "app.ai"`，字段见 `:14-21`）。AGENTS.md 禁止 `@Value` 散落在 Service 里。
4. 本地开发的取巧点：`bootRun` 会逐行解析根目录 `.env` 再注入 JVM 环境变量（`app/build.gradle:107-135`），并强制 UTF-8 编码，省掉手动配环境变量。注意 `application.yml:29-30` 里 `spring.config.import` 导入的是 `optional:classpath:voice-interview-opening.yml`，不是 `.env`。
5. 统一出口：所有异常经 `GlobalExceptionHandler` 转成 HTTP 200 + `Result.error(code, message)`（`app/src/main/java/interview/guide/common/exception/GlobalExceptionHandler.java`）。
6. 版本迁移的真实代价：Boot 4 把 Jackson 升到了 3，包名从 `com.fasterxml.jackson.*` 变成 `tools.jackson.*`。项目里能看到实际写法：
   ```java
   // app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java:11-13
   import tools.jackson.core.JacksonException;
   import tools.jackson.core.type.TypeReference;
   import tools.jackson.databind.ObjectMapper;
   ```

机制顺序（启动到对外服务）：
1. `SpringApplication.run(App.class, args)`（`App.java:28-30`）。
2. Boot 读 `application.yml` + 环境变量 → 绑定 `@ConfigurationProperties`。
3. 自动配置类按条件装配（本项目的 AI 相关被 `exclude` 掉，改为手写 Bean）。
4. 起内嵌 Tomcat（8080，`application.yml:9-10`），请求线程走虚拟线程（2.1）。
5. `@EnableScheduling`（`App.java:17`）打开定时任务；各 Stream 消费者在 `@PostConstruct` 里起线程（2.6）。

**④ 为什么选它 + 代价**
替代方案：手搓 Spring Framework（配置量爆炸）、Quarkus / Micronaut（启动更快、内存更省，AOT 编译友好，但生态和 AI/数据组件成熟度比 Boot 差一截）。选 Boot 的理由就是生态：Spring AI、Spring Data JPA、Springdoc 全都直接可用。
短板要老老实实说：
1. **4.0.1 是很新的大版本**，周边组件都得是刚跟上来的新版本：Spring AI `2.0.0-M4`（还是 Milestone）、spring-ai-agent-utils `0.7.0`、Redisson `4.0.0`。踩坑时文档少，只能读源码。比如 `RedisService.java:251-255` 就是给 Redisson 4.0.0 的一个 bug 打的补丁（无消息时返回 `EmptyList` 而不是空 Map，强转失败）。
2. 自动配置不透明。所以本项目直接 exclude 了 6 个自动配置，宁可自己写 400 行 `LlmProviderRegistry`，也不要"看起来能跑、实际上不确定"。
3. 启动慢、内存高（相对原生编译方案），对一个单体项目可以接受。
【未能核实】Spring Boot 4.0.1 的具体发布日期与官方支持周期。

### 2.3 Spring AI 2.0.0-M4 的五个核心概念

版本：`spring-ai = "2.0.0-M4"`（`gradle/libs.versions.toml`），M 是 Milestone 里程碑版，API 还会变；配套 `spring-ai-agent-utils = "0.7.0"`。依赖里加了 `spring-ai-starter-model-openai`、`spring-ai-starter-vector-store-pgvector`（`app/build.gradle:23-88`）。

#### 概念一：ChatClient

**① 它是什么**
`ChatClient` 是 Spring AI 的对话门面类（fluent API），一行链式调用完成"带系统提示词 → 调模型 → 拿文本/流"。
生活化比喻：餐厅的点单柜台。你只说"要一碗牛肉面"，后厨怎么配（模型选择、温度、顾问链、工具）由柜台去协调。

**② 它解决什么问题**
没有它，你要自己拼 OpenAI 兼容的 JSON、自己管 `messages` 数组、自己处理 SSE 流、自己做错误分类。10 个 LLM 调用点就是 10 份重复的样板代码。

**③ 本项目怎么用它**
三种"配方"，全在 `app/src/main/java/interview/guide/common/ai/LlmProviderRegistry.java`：
1. 默认客户端 `getChatClient(providerId)`（`:103-108`）→ SkillsTool + 可配置 Advisor（`:169-183`）。
2. 纯客户端 `getPlainChatClient(providerId)`（`:133-136`）→ **不带工具**，只加 SafeGuard：
   ```java
   // LlmProviderRegistry.java:185-191
   private ChatClient createPlainChatClient(String providerId) {
       OpenAiChatModel chatModel = getChatModel(providerId);
       ChatClient.Builder builder = ChatClient.builder(chatModel);
       buildSafeGuardAdvisor().ifPresent(advisor -> builder.defaultAdvisors(advisor));
       log.info("[LlmProviderRegistry] Created plain ChatClient (no tools) for {}", providerId);
       return builder.build();
   }
   ```
   注释说明了用途（`:130-132`）："结构化输出场景（出题、简历评分等），要求模型一次性返回可解析 JSON，不应混入工具调用消息"。
3. 语音客户端 `getVoiceChatClient(providerId)`（`:142-145`）→ SkillsTool + 流式 ToolCallAdvisor，**刻意不加 Memory Advisor**（注释 `:138-141`："语音面试手动管理对话历史"）。
实际调用长这样（流式）：
```java
// app/src/main/java/interview/guide/modules/voiceinterview/service/DashscopeLlmService.java:87-91
chatClient.prompt()
    .system(promptContext.systemPrompt())
    .user(promptContext.userPrompt())
    .stream()
    .content()
```
另外：客户端按 provider 缓存在 `ConcurrentHashMap`（`LlmProviderRegistry.java:51-53`），前端改了 Provider 配置就调 `reload()` 清缓存（`:150-156`）；温度默认写死 0.2（`:226-229`），只有 kimi 在 yml 里覆盖成 1（`application.yml:125`）。

**④ 为什么不用框架自带的（自动配置的 ChatClient）**
`spring-ai-starter-model-openai` 会自动造一个 `ChatClient.Builder`，但它绑定 `spring.ai.openai.*` 单一套配置。本项目要 5 个 Provider 共存、运行时切换、API Key 加密入库，所以 `App.java:18-25` 把自动配置全 exclude 掉，自己 new `OpenAiChatModel`。
代价：多写约 430 行（`LlmProviderRegistry.java:1-432`），还要自己维护缓存失效、自己处理"baseUrl 带不带 /v1"（`ApiPathResolver.java:35-38`，用正则判断后改 completionsPath）。

#### 概念二：Advisor

**① 它是什么**
Advisor 是围在 ChatClient 调用外层的拦截器，按 order 串成一条链，可以改请求、改响应、直接拦截。
生活化比喻：机场安检通道。你的行李（prompt 和 response）要依次过几个检查点，任何一个检查点都能把你拦下。

**② 它解决什么问题**
日志、敏感词拦截、工具调用循环、对话记忆这些是横切关注点，不该散落在每个业务 Service 里，否则改一处要改 10 个地方。

**③ 本项目怎么用它**
装配逻辑在 `LlmProviderRegistry.buildDefaultAdvisors(...)`（`:273-308`），按 `app.ai.advisors` 配置逐条判断：
1. `ToolCallAdvisor`（`:281-289` → `buildToolCallAdvisor` `:310-317`）：工具调用的"多轮循环"由它负责。
2. `MessageChatMemoryAdvisor`（`:291-299`）：**默认关**，开了才会挂。
3. `SimpleLoggerAdvisor`（`:301-303`）：**默认关**。
4. `SafeGuardAdvisor`（`:319-330`）：敏感词 6 条（`LlmProviderProperties.java:58-65`），命中就返回固定话术"抱歉，我只能协助面试相关的任务。"，`order(100)`。
配置源（含默认值）：
```yaml
# app/src/main/resources/application.yml:141-148
advisors:
  enabled: ${APP_AI_ADVISORS_ENABLED:true}
  tool-call-enabled: ${APP_AI_ADVISORS_TOOL_CALL_ENABLED:true}
  tool-call-conversation-history-enabled: ${APP_AI_ADVISORS_TOOL_CALL_CONVERSATION_HISTORY_ENABLED:false}
  stream-tool-call-responses: ${APP_AI_ADVISORS_STREAM_TOOL_CALL_RESPONSES:false}
  message-chat-memory-enabled: ${APP_AI_ADVISORS_MESSAGE_CHAT_MEMORY_ENABLED:false}
  message-chat-memory-max-messages: ${APP_AI_ADVISORS_MESSAGE_CHAT_MEMORY_MAX_MESSAGES:120}
  simple-logger-enabled: ${APP_AI_ADVISORS_SIMPLE_LOGGER_ENABLED:false}
```

**④ 为什么这样装配 + 代价**
`ToolCallAdvisor` 的两个开关默认都是 false，是刻意的：出题/评分/评估都是**单轮**调用，把工具调用的中间消息塞回上下文只会让 token 翻倍、还容易让模型跑偏。语音那个客户端才把流式工具响应打开（`:200-203` 传 `buildToolCallAdvisor(true, true)`）。
代价：
1. 关掉"对话历史"意味着模型不记得上一轮自己调过什么工具——本项目靠业务层自己传历史（见概念五）。
2. 不是真正的 Agent 循环。全项目只有语音面试官算真 Agent（工具 + 流式 + 多轮），其余 10 处调用点都是"一次性 prompt 进、结构化结果出"。

#### 概念三：结构化输出 structured output

**① 它是什么**
让模型直接输出"能映射成 Java 对象"的 JSON，而不是一段自然语言。Spring AI 的 `BeanOutputConverter<T>` 负责生成"格式说明"和把 JSON 反序列化成对象。
生活化比喻：不是让客服自由发挥写信，而是递给他一张固定的表格让他填格子。

**② 它解决什么问题**
如果让模型自由输出，再用正则去抠 JSON，会碰到：包在 ```json 代码块里、前面加一句"好的，以下是结果"、字符串里的引号没转义、字段名大小写不一致。任何一条都会让解析炸掉，而且是概率性的炸——今天能跑明天挂。

**③ 本项目怎么用它**
统一入口 `StructuredOutputInvoker.invoke(...)`（`app/src/main/java/interview/guide/common/ai/StructuredOutputInvoker.java:59-106`），配合 `BeanOutputConverter<T>`。四个调用点：
- 出题：`InterviewQuestionService.java:107`（`new BeanOutputConverter<>(QuestionListDTO.class)`）
- 面试评估：`UnifiedEvaluationService.java:84` / `:87`（`BatchReportDTO`、`SummaryDTO`）
- 简历评分：`ResumeGradingService.java:78`
- 岗位 JD 分类：`InterviewSkillService.java:88`
机制顺序（1→5）：
1. system prompt 末尾拼上格式说明：`systemPrompt + "\n\n" + outputConverter.getFormat()`（`InterviewQuestionService.java:203-205`）。
2. 第 1 次调用（`.system(...).user(...).call().content()`，`StructuredOutputInvoker.java:79-83`）。
3. 解析失败先做**本地修复**：把 JSON 字符串里未转义的引号补上转义再解析一次（`:108-129`、修复算法 `:131-181`）。
4. 还失败就第 2 次调用，system prompt 追加"严格 JSON 指令"（`:22-27`）+ 上次的错误原因（`:183-201`，错误信息截到 200 字符，`application.yml:158`）。
5. 两次都失败 → 抛 `BusinessException`（`:101-105`），走全局异常处理。
配置（`application.yml:149-160`）：`structured-max-attempts: 2`、`structured-include-last-error: true`、`structured-retry-use-repair-prompt: true`、`structured-retry-append-strict-json-instruction: true`、`structured-metrics-enabled: true`（指标名 `app.ai.structured_output.invocations/attempts/latency`，`StructuredOutputInvoker.java:29-31`）。
另外注意：Spring AI 自身的重试被关掉了 —— `spring.ai.retry.max-attempts: 1`（`application.yml:78-81`），注释是"禁用自动重试，让异常立即返回"，重试策略统一收到业务层。

**④ 为什么不用框架自带的 `.entity(Class)`**
`ChatClient` 自带 `.entity(SomeClass.class)` 一步到位，但它只有一次机会，且默认客户端挂着工具，工具调用消息会混进上下文影响 JSON 解析。本项目改成：**plain client（无工具）+ 本地引号修复 + 定向重试 + 指标**。
代价：
1. 多一次 LLM 调用就是多一份钱和延迟（尤其评估、评分这种长 prompt）。
2. 重试次数是写死的 2，没有指数退避。
3. 本地方案引入了"修引号"这种兜底逻辑，属于给模型擦屁股——它的边界情况（连续引号、嵌套 JSON 字符串）没有穷尽测试。

#### 概念四：Tool Calling 工具调用

**① 它是什么**
把 Java 方法（或一段可读资源）注册成"模型可以主动申请调用的函数"。模型输出"我要调用 X，参数是 Y"，框架执行完再把结果喂回模型继续。
生活化比喻：给实习生一份"可申请的档案清单"。他自己判断该翻哪本，而不是你提前把所有档案搬到他桌上。

**② 它解决什么问题**
prompt 的长度是有限的、且按 token 计费。本项目每个面试岗位（skill）有一份几千字的 `SKILL.md`（面试官人设、评分偏好、出题风格），如果每次都全塞进 prompt：上下文会爆、费用线性上涨、模型还会被无关岗位的描述干扰。

**③ 本项目怎么用它**
1. 工具 Bean 的构造：
   ```java
   // app/src/main/java/interview/guide/common/ai/AgentUtilsConfiguration.java:29-43
   @Bean("interviewSkillsToolCallback")
   public ToolCallback interviewSkillsToolCallback() {
       String configuredSkillsRoot = agentUtilsProperties.getSkillsRoot();
       String normalizedSkillsRoot = normalizeSkillsRoot(configuredSkillsRoot);
       Resource skillsRootResource = resourceLoader.getResource(normalizedSkillsRoot);
       if (!skillsRootResource.exists()) {
           throw new IllegalStateException("未找到 skills 根目录，请检查配置: " + normalizedSkillsRoot);
       }
       return SkillsTool.builder()
           .addSkillsResource(skillsRootResource)
           .build();
   }
   ```
   `SkillsTool` 来自 `spring-ai-agent-utils`（import 见 `AgentUtilsConfiguration.java:4`）。skills 根目录配置在 `application.yml:104-105`：`skills-root: ${APP_AI_AGENT_UTILS_SKILLS_ROOT:classpath:skills}`。
2. 注册到客户端：`LlmProviderRegistry.java:60` 注入该 `ToolCallback`，`:173-175` 和 `:197-199` 分别给默认客户端、语音客户端挂上（`builder.defaultToolCallbacks(...)`）。plain 客户端刻意不挂（`:185-191`）。
3. 业务侧：`InterviewSkillService`（`app/src/main/java/interview/guide/modules/interview/skill/InterviewSkillService.java`）负责按 skillId 加载技能、算配额、拼基线上限；注释（`:37`）说明分工——"SkillsTool 负责 LLM 按需加载 persona（SKILL.md body）"。

**④ 为什么选 SkillsTool 而不是自己写 `@Tool` 方法**
替代方案：Spring AI 原生的 `@Tool` 注解 + `MethodToolCallback`，把 Java 方法暴露出去。问题是本项目要暴露的不是"算个数"这种函数，而是"读某个 Markdown 作为人设"——这种"按需读资源"的模式，`SkillsTool` 已经封装好了（还带 SKILL.md 的解析约定），自己写等于重造。
代价：
1. 工具调用 = 多一轮模型往返，慢且贵。
2. 工具消息会污染上下文，所以结构化输出场景必须用 plain client，两套客户端并存增加了理解成本。
3. 【未能核实】`classpath:skills` 下具体有哪些技能目录、`SKILL.md` 的正文内容与总字数。

#### 概念五：ChatMemory 对话记忆

**① 它是什么**
把历史对话自动带上，让模型"记得刚才说过什么"。Spring AI 提供 `ChatMemory` 接口 + `MessageWindowChatMemory`（按条数保留最近 N 条）实现，再通过 `MessageChatMemoryAdvisor` 接到调用链上。
生活化比喻：同一个客服带着刚才的通话记录继续聊，而不是每句话都换一个新客服。

**② 它解决什么问题**
不带历史会怎样：模型每次都失忆，用户说"刚才那题再展开讲讲"，它反问"你指的是哪道题"；多轮面试官会重复问同一类问题。

**③ 本项目怎么用它**
框架那套**写了但默认关闭**：
```java
// app/src/main/java/interview/guide/common/ai/LlmProviderRegistry.java:291-299
if (config.isMessageChatMemoryEnabled()) {
    int maxMessages = Math.max(20, config.getMessageChatMemoryMaxMessages());
    MessageChatMemoryAdvisor memoryAdvisor = MessageChatMemoryAdvisor.builder(
        MessageWindowChatMemory.builder()
            .maxMessages(maxMessages)
            .build()
    ).build();
    advisors.add(memoryAdvisor);
}
```
开关默认 false：`application.yml:146`（`APP_AI_ADVISORS_MESSAGE_CHAT_MEMORY_ENABLED:false`），代码里的默认值也是 false 且带注释（`LlmProviderProperties.java:49-51`：`// MessageChatMemoryAdvisor（默认关闭，避免会话串扰）`）。
真正在用的是**手工历史**：
1. 调用方把历史当参数传进来：`DashscopeLlmService.chatStreamSentences(userInput, onToken, onSentence, session, conversationHistory)`（`app/src/main/java/interview/guide/modules/voiceinterview/service/DashscopeLlmService.java:69-73`）。
2. `buildPromptContext(...)`（`:157-179`）里把它拼进用户消息：
```java
// DashscopeLlmService.java:169-177
if (conversationHistory != null && !conversationHistory.isEmpty()) {
    promptBuilder.append("【之前的对话】\n");
    for (String message : conversationHistory) {
        promptBuilder.append(promptSanitizer.sanitize(message)).append("\n");
    }
    promptBuilder.append("\n【当前对话】\n");
}
promptBuilder.append("用户：").append(
    promptSanitizer.wrapWithDelimiters("input", promptSanitizer.sanitize(userInput)));
```
3. 每条历史都过 `PromptSanitizer`（调 sanitize，用户输入再套一层随机边界标签），这是防提示词注入的一部分。

**④ 为什么不用框架自带的 ChatMemory**
1. `MessageWindowChatMemory` 默认是**进程内内存**实现：重启就丢、多实例不共享，而本项目会话数据要跨请求、跨重连（缓存层是 Redis，`InterviewSessionCache`）。
2. Advisor 是挂在客户端上的，客户端按 provider 缓存在 `ConcurrentHashMap` 里全局共用（`LlmProviderRegistry.java:51-53`）——同一个客户端给所有会话用，记忆很容易串到别人身上。所以代码注释写的是"避免会话串扰"。
3. 语音链路本来就需要"每轮重放历史 + 可能截断 + 每句都要做注入清洗"，干脆自己管。
代价：自己管就要自己保证长度可控，长会话 token 会持续上涨；而且历史拼接是自己写的，没有框架那套消息角色（user/assistant）区分，只是纯文本块。
【未能核实】语音面试历史在传给 LLM 前的具体截断策略（条数或字符数上限）——`DashscopeLlmService` 里只看到逐条 sanitize，没看到截断。

### 2.4 PostgreSQL 16 + pgvector（向量数据库）

**① 它是什么**
先解释四个名词，都是面试必问：
- **向量**：一串有顺序的数字。比喻：把每句话变成"地图上的一个坐标点"，意思越接近，点挨得越近。
- **embedding（嵌入）**：把一段文字"翻译"成向量的模型/过程。本项目用的是阿里云 `text-embedding-v3`（`application.yml:111`）。
- **1024 维**：这个向量有 1024 个数字，也就是坐标有 1024 个轴，每个轴一个 float（4 字节）→ 一条向量约 4KB。
- **余弦距离**：只看两个向量"夹角"多大，不看长度长短。夹角越小越像。值越小表示越相似。
- **HNSW 索引**：一种图索引（分层可导航小世界），查询时像走"跳表"一样逐层跳着找近邻，避免把几万条向量全算一遍。比喻：图书馆不是逐本翻，而是先看分区指示牌再进书架。
本项目就是 PostgreSQL 16 装一个 `pgvector` 扩展，让关系库同时具备向量检索能力。

**② 它解决什么问题**
RAG（检索增强生成）的核心是"先检索、再生成"。没有向量检索会怎样：
1. 用 `LIKE '%关键词%'` 检索：用户问"垃圾回收停顿怎么排查"，文档里写的是"GC 暂停时间调优"，词对不上就检索不到。
2. 把整篇文档塞进 prompt：超上下文、超预算。
向量检索解决的是"按语义相似度找片段"这件事。

**③ 本项目怎么用它**
1. 基础设施：镜像用带扩展的 `pgvector/pgvector:pg16`（`docker-compose.yml:15`，不是官方 `postgres` 镜像），初始化 SQL 只有一行：
   ```sql
   -- docker/postgres/init.sql:1
   CREATE EXTENSION IF NOT EXISTS vector;
   ```
2. 向量库配置：
   ```yaml
   # app/src/main/resources/application.yml:83-89
   vectorstore:
     pgvector:
       index-type: HNSW
       distance-type: COSINE_DISTANCE
       dimensions: 1024  # text-embedding-v3实际生成的向量维度
       initialize-schema: true
       remove-existing-vector-store-table: false
   ```
3. EmbeddingModel 用的是"委托"写法：Spring AI 的 VectorStore 需要一个 `EmbeddingModel` Bean，本项目给的是一个转发到 `LlmProviderRegistry` 的匿名实现（`app/src/main/java/interview/guide/common/config/LlmEmbeddingConfig.java:16-30`），这样向量化自动跟着运行时选中的 Provider 走。
4. 写入链路（`app/src/main/java/interview/guide/modules/knowledgebase/service/KnowledgeBaseVectorService.java`）：
   1. 先删该知识库旧向量（`:49-50`）。
   2. 切块：`TokenTextSplitter.builder().build()`（`:38`），注释写明"每个 chunk 约 800 tokens，基于标点边界切分（无重叠）"。
   3. 每块塞 metadata `kb_id`（`:59-61`，统一存 String 保证查询一致）。
   4. 分批向量化，每批最多 10 个（`MAX_BATCH_SIZE = 10`，`:30`，注释说明是 DashScope 的 API 限制），调 `vectorStore.add(batch)`（`:62-73`）。
   5. 整个方法带 `@Transactional`（`:45`）。
5. 检索链路：`similaritySearch(query, knowledgeBaseIds, topK, minScore)`（`:91-125`）→ 构造 `SearchRequest`，带 metadata 过滤表达式 `kb_id in [...]`（`:176-183`）→ `vectorStore.similaritySearch(...)`。过滤失败时回退到"先多取 3 倍再本地过滤"（`:127-159`，`topK * 3`，`:132`）。
6. 删除用原生 SQL 直删（`app/src/main/java/interview/guide/modules/knowledgebase/repository/VectorRepository.java:41-45`）：
   ```sql
   DELETE FROM vector_store
   WHERE metadata->>'kb_id' = ?
      OR (metadata->>'kb_id_long' IS NOT NULL AND (metadata->>'kb_id_long')::bigint = ?)
   ```
   注释（`:36-40`）记了个真实的坑：`metadata` 是 JSON 类型不支持 `jsonb_exists`，且要绕开 PostgreSQL 的 `?` 操作符以免和 JDBC 占位符冲突。
7. 检索参数是自适应的（`application.yml:161-169`）：短问句（≤4 字）topK 20、minScore 0.18；中等（≤12 字）topK 12、0.28；长问句 topK 8、0.28。

**④ 为什么选它 + 代价（为什么不用 Milvus）**
替代方案一：**Milvus**。它是专用向量数据库，召回和规模确实强，但要单独部署一整套（还要 etcd、对象存储），多一套运维、多一份资源、多一个 SDK，且向量和业务数据分家——删知识库时得保证两边都删成功。
替代方案二：Elasticsearch 的 kNN、或 FAISS 本地索引。前者引入一个大组件，后者没有持久化与并发能力。
选 pgvector 的理由：
1. 架构里本来就有 PostgreSQL（存简历、面试会话），加个扩展即可，`docker-compose.yml:15` 只换了镜像标签，`init.sql:1` 一行。
2. **向量和业务数据同一个库、同一个事务**——`vectorizeAndStore` 上直接挂 `@Transactional`，删知识库时删向量和删业务行能一起回滚。
3. 运维成本近似为零。
短板（要主动说）：
1. 向量规模上到千万级时，HNSW 索引占内存，召回率和延迟调优手段不如专用库丰富；本项目数据量（个人知识库/文档）远不到这个量级。
2. pgvector 的"过滤 + 向量"混合查询能力弱：只能用 metadata 条件，过滤走不动索引就得回退到"多取再本地筛"（`KnowledgeBaseVectorService.java:127-159`）。
3. 维度写死 1024（`application.yml:87`）。换 embedding 模型（比如输出 1536 维）就要重建向量表和全部数据。
4. 切块无重叠（`:38` 注释）+ 没有 Rerank 环节，是当前检索质量的已知短板。
【未能核实】数据库里实际的表名、HNSW 索引名与索引是否已建立（没有连库执行 `\d` 验证；表名 `vector_store` 来自 `VectorRepository.java:26-27` 的注释和 `:42` 的 SQL）。

### 2.5 Redis 7：缓存与会话

**① 它是什么**
Redis 是内存键值数据库，支持字符串、哈希、列表、有序集合、Stream 等结构，支持 TTL 自动过期。
生活化比喻：贴在冰箱门上的便签。写上去快、看得快，但它是便签——会被撕掉、会过期，不能当唯一账本。

**② 它解决什么问题**
模拟面试的会话状态（题目列表 JSON、当前第几题、状态、简历原文）如果每次都读数据库：
1. 每次答题都要 JOIN 几张表 + 反序列化，慢。
2. "这个简历还有没有未完成的面试"需要一条关系查询。
3. 数据没有自动过期机制，历史会话必须靠定时任务清理。
这三条正是 Redis 的强项：点查、二级索引式映射、TTL。

**③ 本项目怎么用它**
1. 版本与部署：镜像 `redis:7`（`docker-compose.yml:48`），带 `redis-cli ping` 健康检查（`:54-58`），app 依赖它 healthy 才启动（`:131-135`）。
2. 客户端是 Redisson，配置在：
   ```yaml
   # app/src/main/resources/application.yml:64-74（节选）
   redis:
     redisson:
       config: |
         singleServerConfig:
           address: "redis://${REDIS_HOST:localhost}:${REDIS_PORT:6379}"
           database: 0
           connectionMinimumIdleSize: 10
           connectionPoolSize: 64
           subscriptionConnectionPoolSize: 50
   ```
3. 统一封装：`app/src/main/java/interview/guide/infrastructure/redis/RedisService.java`（`set/get/delete/expire/exists` 见 `:45-107`）。
4. 会话缓存本体：`app/src/main/java/interview/guide/infrastructure/redis/InterviewSessionCache.java`
   - key 前缀 `interview:session:`（`:35`）
   - 简历→会话映射前缀 `interview:resume:`（`:40`）
   - TTL 固定 24 小时：`private static final Duration SESSION_TTL = Duration.ofHours(24);`（`:43-45`）
   - 缓存的实体是 `CachedSession`，里面放 `resumeText`、`questionsJson`（问题列表序列化后的字符串）、`currentIndex`、`status`（`:50-84`）
5. 使用方与流程（`app/src/main/java/interview/guide/modules/interview/service/InterviewSessionService.java:45` 注入）：
   1. 建会话 → `saveSession(...)` 写 session key，若状态未完成再写 `interview:resume:{resumeId}` 映射（`InterviewSessionCache.java:89-105`）。
   2. 答题 → `updateCurrentIndex(...)`（`:141-148`）、`updateQuestions(...)`（`:153-164`），都是"读出来改完再整体写回"。
   3. 完成 → `updateSessionStatus(...)`，同时删掉 resume 映射（`:123-136`）。
   4. 断线重连 → `findUnfinishedSessionId(resumeId)`（`:184-198`）：查映射拿到 sessionId，再校验会话仍存在、状态仍是 `CREATED`/`IN_PROGRESS`（`:240-242`），否则顺手清理脏映射。
   5. 续期 → `refreshSessionTTL(...)`（`:203-206`）。

**④ 为什么选它 + 代价**
替代方案一：**Caffeine 本地缓存**。进程内、纳秒级，但重启即丢、多实例各存一份会不一致，且没有 TTL 之外的跨节点可见性。
替代方案二：直接把会话状态存 PostgreSQL。能做，但每次答题加一次写库 + JSON 反序列化，且"未完成会话查找"要写额外查询，还要自己写清理任务。
选 Redis 的理由：多实例共享、原生 TTL、而且后面异步队列（2.6）和限流（2.8）也用同一个实例，不新增组件。
代价（必须承认）：
1. 缓存层没有本地兜底：Redis 不可用，会话相关的接口直接报错。
2. 缓存与数据库的**一致性靠"缓存为主 + 24h TTL 兜底"**，不是强一致。`updateQuestions` 是"读-改-写"，并发下会丢更新（没有加锁或 CAS）。
3. 缓存里存了简历原文（`resumeText`，`:53`），等于敏感数据进内存并被序列化，24 小时内都在 Redis 里。
4. **诚实说明**：`RedisService` 里还封装了 Hash、List、原子计数器、分布式锁等方法（`:109-207`、`:339-378`），但全库检索后确认，除 Stream（`:209-337`）之外这些方法在主干业务代码里**没有调用点**。所以不能说"本项目用 Redis 做计数器"。
【未能核实】Redis 是否承担了语音面试模块的会话/计数职责（在全项目检索 `RedisService` 只找到 8 个 Stream 生产/消费者类和 `InterviewSessionCache`，未发现语音模块使用）。

### 2.6 Redis Stream：异步消息队列

**① 它是什么**
Redis Stream 是 Redis 5 引入的"只追加日志 + 消费组"结构，可以做消息队列。
- **Stream**：一条条按 ID 顺序追加的消息。
- **消费组（consumer group）**：一组消费者共享一个 Stream，同一条消息只会被组内一个消费者拿到，天然不重复劳动。
- **ACK**：处理完显式签收。
- **Pending（PEL，待处理列表）**：已投递但没 ACK 的消息清单，消费者挂了可以重新认领——这就是"至少一次投递"的保障。
生活化比喻：公司收发室的收件登记本。每封信有编号，谁取走了要在本子上签收（ACK）；没签收的信还挂在"待领"名单里。

**② 它解决什么问题**
本项目的异步任务都很慢：文档向量化要切块 + 多次调 embedding API；面试评估要按 batch 调 LLM 好多轮（batch-size 8，`application.yml:168`）。同步做的话：
1. HTTP 请求几十秒起步，前端超时、用户体验差（Nginx 默认 60s 就可能 504）。
2. 服务重启进行中的任务全丢。
3. 无法限流、无法重试。

**③ 本项目怎么用它**
1. 生产者模板（`app/src/main/java/interview/guide/common/async/AbstractStreamProducer.java:22-36`）：`sendTask(...)` → `redisService.streamAdd(streamKey(), buildMessage(payload), STREAM_MAX_LEN)`，发送异常走 `onSendFailed` 把业务状态标 FAILED。
2. 消费者模板（`app/src/main/java/interview/guide/common/async/AbstractStreamConsumer.java`）：
   - `@PostConstruct init()`（`:30-50`）起一个**单线程** `ThreadPoolExecutor`（核心/最大都是 1，`:33-45`，名字带 `consumerName = 前缀 + UUID 前 8 位`，`:32`），守护线程。
   - `consumeLoop()`（`:72-91`）循环调用阻塞读，异常时 `log.error` 后继续。
   - 处理单条消息的顺序（`:93-121`）：解析 payload（解析不出来直接 ACK 丢弃）→ 读 `retryCount` → `markProcessing` → `processBusiness` → `markCompleted` → ACK；抛异常则判断 `retryCount < MAX_RETRY_COUNT` → `retryMessage(payload, retryCount + 1)`，否则 `markFailed(...)`（错误信息截断到 500 字符，`:131-136`）；**两种情况最后都 ACK**。
3. 常量（`app/src/main/java/interview/guide/common/constant/AsyncTaskStreamConstants.java`）：最大重试 3 次（`:30`）、批量 10（`:35`）、轮询阻塞 1000ms（`:40`）、Stream 最大长度 1000（`:45`，自动裁剪旧消息防无限增长）。

**④ 为什么不用 RocketMQ / Kafka**
替代方案的**问题**：
- Kafka：要部署 broker + ZooKeeper/KRaft，堆内存几个 G，运维一套监控；本项目的消息量是"每天几十条向量化 + 几十次评估"，用它等于用航母运快递。
- RocketMQ：部署 NameServer + Broker，组件更多，还要引入客户端依赖和事务消息概念。
- RabbitMQ：比 Kafka 轻，但仍是独立组件，且没有 Stream 这种"消息可回放、可按时间查"的自然模型。
选 Redis Stream 的理由：
1. Redis 本来就在架构里（缓存需要它），不用新增中间件，`docker-compose.yml:47-58` 一个服务搞定。
2. Stream 自带消费组、ACK、Pending，可靠性和"至少一次"语义已经够本项目用。
3. 客户端已经有 Redisson，不用再加 MQ SDK。
代价与短板：
1. 没有专业 MQ 的堆积告警、死信队列、延迟队列、严格顺序消费（本项目不需要严格顺序，但要知道这个边界）。
2. Stream 长度靠 `STREAM_MAX_LEN = 1000` 裁剪（`AsyncTaskStreamConstants.java:45`），消息爆量会丢老消息（对已完成、已 ACK 的消息无所谓，但排查问题时会发现历史消息没了）。
3. "重试"是应用层自己重新 `add` 一条新消息，不是 Redis 原生的 `XCLAIM` 重投，所以重试会产生新消息 ID，Pending 列表并不反映真实重试次数（真实次数在消息体的 `retryCount` 字段里）。
4. 每个消费者实例只跑 1 个消费线程（`AbstractStreamConsumer.java:33-45`），吞吐靠"多实例 + 消费组"横向扩，单实例内不并行。
5. 【未能核实】线上是否真的跑过多个应用实例验证消费组的分摊行为（部署配置里只有一个 `app` 服务，见 `docker-compose.yml:125-170`）；也未找到补偿"消费者崩溃后 pending 消息重新认领"的逻辑（代码里只用 `neverDelivered()` 读新消息）。

### 2.7 Redisson：分布式锁与协调

**① 它是什么**
Redisson 是 Redis 的 Java 客户端，但它不是简单的命令封装，而是把分布式场景的"难点封装"做完了：可重入锁（`RLock`）、看门狗自动续期、信号量、分布式集合、以及本项目重度使用的 `RStream`（Stream）和 `RScript`（Lua 脚本执行）。
生活化比喻：它不是给你一把钥匙，而是给你一整套**门禁系统**——刷卡记录、自动续期、超时自动开门。

**② 它解决什么问题**
以"分布式锁"为例，如果手写 `SETNX` + `EXPIRE`，有三个经典坑：
1. `SETNX` 和 `EXPIRE` 是两条命令，中间进程挂掉 → 锁永远不释放（死锁）。
2. 业务没跑完锁就到期 → A 和 B 同时持锁，互斥失效。
3. A 释放时可能删掉 B 的锁（要先比对 value 是否是自己的，这个"比对 + 删除"必须原子，就得又拼 Lua）。
Redisson 的 `RLock` 用 Hash 结构存"持有者线程 ID + 重入次数"，并带看门狗（默认 30 秒续期），上述三个坑都不用手写。

**③ 本项目怎么用它**
1. 依赖与配置：`redisson-spring-boot-starter`（版本 `redisson = "4.0.0"`，`gradle/libs.versions.toml`）；连接参数 `application.yml:64-74`（单机模式、连接池 64、订阅连接池 50）。
2. 封装层（`app/src/main/java/interview/guide/infrastructure/redis/RedisService.java:151-207`）：
   - `getLock(lockKey)`（`:156-158`）
   - `tryLock(lockKey, waitTime, leaseTime, unit)`（`:163-171`，被中断时恢复中断标志并返回 false）
   - `unlock(lockKey)`（`:176-181`，先 `lock.isHeldByCurrentThread()` 再解锁，避免解别人的锁）
   - `executeWithLock(lockKey, waitTime, leaseTime, unit, operation)`（`:186-202`）：拿不到锁直接抛 `BusinessException(ErrorCode.INTERNAL_ERROR, "获取锁失败: " + lockKey)`
3. **必须诚实说明的现状**：这层锁 API 目前**在主干业务代码里没有调用点**（全项目检索 `getLock/tryLock/executeWithLock`，只有 `RedisService` 自身的定义）。
   项目里真正用到 Redisson 的地方是：
   - Stream：`RStream.readGroup/add/ack/createGroup`（`RedisService.java:239-337`）——4 条异步管道全靠它（见 2.6）。
   - Lua 脚本执行：`RScript.scriptLoad/evalSha`（`RateLimitAspect.java:54`、`:59`、`:103`）——限流全靠它（见 2.8）。
   - 普通缓存：`RBucket`（`RedisService.java:45-107`）——面试会话缓存（见 2.5）。
   - 锁：已封装、待接入。
4. `RScript` 的用法值得单独讲，因为它示范了"客户端要替服务端擦屁股"：
   ```java

   Object resultObj = rScript.evalSha(RScript.Mode.READ_WRITE, luaScriptSha,
       RScript.ReturnType.VALUE, keysList, args);
   ...
   } catch (org.redisson.client.RedisException e) {
       // Redis 重启后脚本缓存丢失，重新加载并重试
       if (e.getMessage() != null && e.getMessage().contains("NOSCRIPT")) {
           loadScript();
           // 重新 evalSha
   ```
   先用 `scriptLoad` 拿 SHA1（`:58-61`），后续发 SHA 省带宽；Redis 重启后缓存清空会报 `NOSCRIPT`，捕获后重新加载再试。

**④ 为什么不用手写 `SETNX`（为什么是 Redisson）**
1. 手写的三条坑上面说过，Redisson 已经解决（原子加锁、看门狗续期、持有者校验解锁）。
2. 本项目还需要 Stream 和 Lua 脚本执行，Redisson 一家全包（`RStream`、`RScript`），不用同时引 Lettuce/Jedis 两套。
3. Redisson 还有 `connectionMinimumIdleSize: 10`、`subscriptionConnectionPoolSize: 50` 这类连接池参数（`application.yml:71-74`），生产可控。
代价与短板（要能自己说）：
1. **抽象不透明**：看门狗续期、重入语义、`leaseTime` 传不传的行为差异，都要懂才敢用；不懂就容易以为"加了锁就万事大吉"。
2. `redisson 4.0.0` 是新大版本，本项目已经踩到一个真实 bug：`RedisService.java:251-255` 给"无消息时返回 `EmptyList` 而非空 Map"打补丁。
3. RLock 是**单实例锁**（配置是 `singleServerConfig`），不是 RedLock。Redis 主从切换的极端窗口内理论上可能同时两人持锁——本项目单机 Redis，风险可控，但这是知识边界。
4. 加锁意味着"无锁化设计"这条路被放弃了，热点 key 会成为吞吐瓶颈。
5. 【未能核实】`RLock` 看门狗续期在本项目的实际表现（因为没有任何调用点，等于未在生产路径验证过）；也未能核实没有业务调用点的原因是"预留"还是"曾被删掉"。

### 2.8 Redis Lua + AOP 限流

**① 它是什么**
- **限流**：限定单位时间内某个维度的请求次数，超了就拒绝或降级。比喻：景区闸机，一分钟只放 10 个人进去。
- **AOP（面向切面编程）**：把"限流"这种横切逻辑从业务代码里抽出来，用一个注解 + 一个切面自动套上。比喻：不用每扇门都装保安，而是在走廊装一道闸机。
- **固定窗口 vs 滑动窗口**：
  - 固定窗口：按自然分钟/秒切分计数。漏洞是边界可以刷双倍——第 59 秒打满 10 次，第 0 秒再打满 10 次，1 秒内过了 20 次。
  - 滑动窗口：看"最近 N 毫秒"内的请求。本项目用的是滑动窗口（Lua 注释 `app/src/main/resources/scripts/rate_limit_single.lua:2`："基于滑动时间窗口的单维度原子限流"）。
- **令牌桶**：桶里放固定数量令牌，每个请求拿走一个；本项目的实现是"过期的令牌会被回收加回来"，不是匀速生成令牌。
- **原子性为什么重要**：如果分成"先 GET 看剩几个 → 再 SET 扣减"，两步之间会有别的请求插进来。两个实例同时看到"还剩 1 个"，就都放行 → 超发。所以"读-算-写"必须在一次不可分割的执行里完成。
- **为什么必须写在 Lua 里**：Redis 执行 Lua 脚本时是单线程、不被打断的；而且脚本内的多条命令只算一次网络往返（RTT）。放在 Java 里做，即使加锁也会多几次 RTT，且锁本身又要抢 Redis。

**② 它解决什么问题**
1. LLM 调用是按 token 花真金白银的：不限制的话，一个脚本刷接口就能把 API 额度打完。
2. 语音面试要建 WebSocket + 起 ASR/TTS 实时连接，单机资源有限，必须挡刷子。
3. 多实例部署时，用 `AtomicInteger` 或 Guava 计数是"每个实例各限一份"，实际放行 N × 实例数——相当于没限。

**③ 本项目怎么用它**
1. 注解定义：`app/src/main/java/interview/guide/common/annotation/RateLimit.java`
   - `@Repeatable(RateLimit.Container.class)`（`:29`，容器定义 `:114-118`）→ 一个方法可以挂多条规则，每条独立 `count/interval/timeUnit`。
   - 维度枚举 `Dimension`：`GLOBAL`（全局）/ `IP` / `USER`（`:35-48`）。
   - 参数：`count`（必填，`:64`）、`interval`（默认 1，`:72`）、`timeUnit`（默认 `SECONDS`，`:80`）、`timeout`（默认 0=不等待，`:89`）、`fallback`（降级方法名，默认空，`:102`）。
   - 注释明确语义（`:16`）："同一方法上可标注多个 @RateLimit，所有规则必须全部通过才允许请求"。
2. 切面：`app/src/main/java/interview/guide/common/aspect/RateLimitAspect.java`
   ```java

   RateLimit[] rules = method.getAnnotationsByType(RateLimit.class);
   long nowMs = System.currentTimeMillis();
   ```

   - Key 设计（`:154-163`）：`ratelimit:{ClassName:MethodName}:global` / `:ip:{ip}` / `:user:{id}`。**大括号是 Hash Tag**——保证同一个方法的多条规则落在同一个 Redis cluster slot（本项目单机，但这个设计是为将来分片准备的）。

   - 两个 Redis key（`:20-21`）：`:value`（字符串，存当前剩余令牌）、`:permits`（ZSET，成员是 `requestId:permits`，score 是时间戳）。
   - 核心四步：
   ```lua
   -- rate_limit_single.lua:24-27, 37-42, 45-52（节选）
   local current_val = tonumber(redis.call("get", value_key)) or max_tokens
   local expired_values = redis.call("zrangebyscore", permits_key, 0, now_ms - interval)
   if #expired_values > 0 then
       -- 累加过期令牌数，再从 ZSET 移除
       redis.call("zremrangebyscore", permits_key, 0, now_ms - interval)
       current_val = math.min(max_tokens, current_val + expired_count)
   end
   if current_val < permits then
       return 0
   end
   local permit_record = request_id .. ":" .. permits
   redis.call("zadd", permits_key, now_ms, permit_record)
   redis.call("set", value_key, current_val - permits)
   ```

   返回 `1` = 放行，`0` = 拒绝。

机制顺序（一次请求）：
1. 请求打到 Controller 方法 → Spring AOP 命中 `@Around("@annotation(...RateLimit) || @annotation(...RateLimit.Container)")`（`RateLimitAspect.java:66-67`）。
2. 取出该方法上所有 `@RateLimit` 规则（`:74`），生成一次性的 `requestId`（`:76`）。
3. 逐条规则算 intervalMs 和 Redis key（`:79-80`）。
4. 每条规则调用同一个 Lua 脚本（一次 `evalSha`）（`:103-109`）。
5. 任一条返回 0 → 走降级或抛异常（`:84-86`）。
6. 全部通过 → `joinPoint.proceed()` 执行真正的业务方法（`:89`）。

**④ 为什么选它 + 代价**
替代方案一：**Guava `RateLimiter`**。单机内存计数，多实例各限一份，直接失效；且它按"每秒生成令牌"的桶模型，想要"每分钟 10 次"这种窗口语义还得自己算。
替代方案二：**Sentinel / 网关层限流（Nginx limit_req）**。Sentinel 功能强但要多部署 Dashboard、规则要单独维护、动态规则又是一套数据源；Nginx 层限流只能按 IP/连接数、拿不到"按用户维度"和"按方法维度"的信息。本项目需要"每个接口独立配置 + 多维度同时生效 + 触发后能降级"，注解 + AOP + Lua 正好贴合。
选它的好处：限流状态天然全局一致（在 Redis 里）、零新增部署、加限流只加一行注解。
代价（要主动交代）：
1. **时间戳由应用侧传入**（`ARGV[1] = System.currentTimeMillis()`，`RateLimitAspect.java:75`、`:95`）。多实例之间时钟不同步，窗口计算就会有偏差。更稳的写法是在 Lua 里用 `redis.call("time")` 取服务端时间。当前写法是设计取舍也是缺陷。
2. 每个维度一次 Redis 往返。一个方法挂 2 条规则就是 2 次 RTT，压测时这是实打实的延迟。
3. 脚本 SHA 缓存会因 Redis 重启失效，必须靠 `NOSCRIPT` 兜底重载（`:111-125`）——多了一条异常路径。
4. `fallback` 靠反射匹配方法，参数不匹配只打一条 warn 日志（`:208-210`），配错了会静默失效，排查不直观。
