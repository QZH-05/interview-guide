## 第 1 部分 · 一句话电梯介绍（30 秒）

> 我做的项目叫 **InterviewGuide**，是一个 AI 面试官平台。
>
> 起因挺实际的：我自己准备面试的时候，想找人模拟面试成本特别高——要凑时间，还得对方刚好懂技术。市面上那种 AI 面试工具我也用过，大部分就是把简历丢给大模型让它出题，问得很泛，而且它记不住你上一轮答了什么，第二轮开始就重复。
>
> 所以我这个项目主要解决两件事：**一是让 AI 真的能一问一答、还能追问**；**二是让评估有依据**——不是让模型随便打个分，而是先给它一份评分标准表和这个方向的参考答案基线，逐题打分，总分用代码算，不让模型自己算数。
>
> 技术上后端是 Java 21 + Spring Boot 4.0.1 + Spring AI，存储用的 PostgreSQL + pgvector 和 Redis，语音那条链路接的是 DashScope 的 Qwen3 实时模型。后端大概 173 个类、一万九千行左右，我一个人负责架构和核心模块。【口径待确认 P2】

**⚠️ 三条纪律（进门就定调）**
1. **绝对不说"多 Agent 协作"**。正确表述："1 个真 Agent（语音面试官，带工具调用循环）+ 若干条由 Java 编排的 LLM 流水线"。
2. **不说"我用了个限流 / 我做了个 RAG"**，要说"`@RateLimit` 注解 + Redis Lua 滑动窗口，GLOBAL/IP/USER 三个维度独立计数"。
3. **不说 MySQL、不说 Python、不说 LangChain**（这个项目里都没有，见第 4 部分）。

## 第 2 部分 · 核心功能逐个讲（每个 2 句，约 2 分钟）

### ① 简历上传 → 解析 → 结构化分析

> 简历上传后先存到对象存储拿到地址，然后**发一条 Redis Stream 消息**，异步去做解析——因为解析一份 PDF 要十几秒，不能让前端干等。消费者里用 **Tika** 把 PDF/Word 抽成文本，再用 `TextCleaningService` 清掉页眉页脚、乱码这些脏数据，最后让模型把简历抽成结构化字段。

**追问时补**：异步管道是统一的模板——`AbstractStreamProducer` / `AbstractStreamConsumer`，**四条管道**（知识库向量化、简历分析、文本面试评估、语音面试评估）共用一套重试和状态机，失败重试 3 次后标 `FAILED`；每批拉 10 条、Stream 长度上限 1000 条自动裁剪；处理前先校验实体还在不在，不在就直接 ACK 丢掉，避免无效重试。

### ② 文本面试出题（Skill 驱动 + 确定性配额）

> 出题我**没有**把简历直接丢给模型自由发挥。我在 `resources/skills` 下面按技术方向放了 10 个技能目录，每个目录里有描述"这个方向考什么"的 SKILL.md 和出题参考基线；加载完之后按类目做**确定性配额**——比如 Java 基础出几题、项目经历出几题，用 `LinkedHashMap` 保序生成配额，再把简历、参考基线、以及**已经问过的题目摘要**一起注入提示词。

**追问时补**：参考基线上限总 12000 字符、单文件 3000 字符，防上下文过载；历史题按类型分组注入，让模型自己看出"这个方向已经问过 5 题了"，不直接堆一长串题目；追问走 `parentQuestionIndex` 挂成一棵树，默认每题追问 1 次。

### ③ 问答 + 统一评估引擎（**最值得讲的一块**）

> 评估这块我做得最认真。**文本面试和语音面试共用同一个 `UnifiedEvaluationService`**——因为两者的评分维度、分批逻辑、汇总逻辑完全一样，差的只是输入从哪来。流程是这样：先固定一份 rubric，准确性 40、完整性 20、深度 25、表达 15；然后按**每批 8 道题**分批调用，避免一次塞太多题导致中间几题被忽略；**每题只让模型给逐题分和文字反馈，总分和类目均分全部由代码算**——因为模型做算术不可靠，它自己算就会出现"逐题分加起来跟总分对不上"。最后一步汇总只生成评语、不带分数，而且汇总失败能回退到代码聚合的结果。

**追问时补**：无效回答（"不知道""忘记了"）强制 0 分，防止模型出于礼貌给分；缺位的题目按 0 分占位而不是删掉——删了分母变小，等于失败反倒把均分拉高；评分 prompt 里注入该方向参考答案基线（上限 6000 字符）让打分有依据。

### ④ 知识库 RAG 问答

> 文档上传后先用 `TokenTextSplitter` 按标点切成大约 800 token 的块，用 `text-embedding-v3` 打成 1024 维向量存进 pgvector，索引是 HNSW、距离用余弦。查询这条链路我做了两个设计：**一是先做查询改写，把"它""这个"这种指代补全，然后改写后的问题和原始问题都拿去检索，谁先命中有效的就用谁**；**二是检索参数按问题长度自适应**——4 个字以内的短问题我把 topK 放宽到 20、阈值降到 0.18，因为短查询语义信息少，卡太紧就什么都召不回来。

**追问时补**：流式输出加了 **120 字符的探测窗口**，如果模型开头就说"没有找到相关信息"，直接掐断上游、换成兜底回复，不让它开始编；检索异常还有一条兜底——按 topK×3 召回再截断回 topK。

### ⑤ 语音面试实时链路（**差异化最强**）

> 浏览器这边用 `getUserMedia` 开回声消除拿到音频，用 **AudioWorklet** 在独立音频线程里重采样成 16kHz PCM，**每 200 毫秒一块**、base64 编码走 WebSocket 发给后端；后端接 DashScope 的实时 ASR（服务端 VAD 自动断句），定稿的句子再送流式 LLM，**边收边按句子切开，每切出一个完整句子就立刻启动这句的 TTS**，用 `Semaphore` 限制单会话最多 3 个并发合成。这样"生成"和"合成"是并行的，不是串行等生成完再合成。

**追问时补**：所以 TTS 首包延迟从约 500ms 降到 200ms；单句合成超时 8 秒，前端还有播放看门狗（按 WAV 头算时长 +1.5 秒，上限 60 秒）防止"AI 永远不说话"。

### ⑥ 多模型管理 + 限流

> 模型不是写死的，我抽了一层 `LlmProviderRegistry`，支持 DashScope、Kimi、DeepSeek、GLM 和本地 LM Studio，API Key 加密后入库、在设置页里管理。限流是自己写的 `@RateLimit` 注解加 AOP，做成了 `@Repeatable`，所以 GLOBAL、IP、USER 三个维度可以叠加在同一个方法上，每个维度调一次 Redis Lua 脚本，**滑动窗口 + 令牌桶，读-判断-写在 Lua 里原子完成**。

**追问时补**：Redis Key 用 Hash Tag 分组 `ratelimit:{类名:方法名}:维度`；不用固定窗口是因为固定窗口在临界点会双倍放行。

## 第 3 部分 · 重难点（3 个，三段式，约 2 分钟）

### 难点一：怎么判断"用户说完了"——以及随之而来的 AI 自问自答

**难点是什么**
> 语音面试真正难的不是识别准不准，是**轮次边界**。说早了 AI 抢话，用户刚想两秒它就开口；说晚了用户干等。更麻烦的是第二种情况：AI 自己的声音会被麦克风收回来，被 ASR 当成"用户在说话"，于是 AI 开始自己跟自己对话。

**我怎么解决**
> 我做的是**三层接力 + 四层回声防护**。三层是：服务端 VAD 静音 2 秒切段；切出来的多个段落先不急着送模型，用拼接逻辑做重叠去除和标点合并，因为口语里"嗯…那个…"会被切得七零八落；最后**由用户点"提交回答"来决定轮次边界**。四层回声防护是：采集端本地不回放自己的声音（`gainNode.gain = 0` 加 `echoCancellation`）；前端在 AI 说话时干脆不发音频；服务端在 AI 说话期间和播放结束后加 800ms 冷却期，直接丢输入；AI 处理期间迟到的识别结果也直接丢。

**踩过什么坑**
> 我一开始上的是**全自动提交**，结果用户只是思考停顿一下，AI 就开始回答了，体验特别差；反过来把静音阈值调大，又变成"等太久"。所以最后我把**决定权交给了用户**——现在真正生效的机制就是"用户手动点提交"。我还设计过一组"防过早"参数（最少 20 字、最少静音 2.5 秒、最长等 7 秒），**但那四项配置至今没有接线，Java 代码里从来没读过它们，属于死配置**——这是我已知的待修项，我不会把它当成已实现的功能来讲。另外回声我是分四层防的，因为我发现它不是一个单点问题：采集端会产生、网络端音频已经在路上、时序上识别结果还会迟到，每一层的失效模式不一样。

### 难点二：大模型的输出不可控——格式漂移 + 算错账

**难点是什么**
> 让模型按固定 JSON 返回，还要它自己算总分，会踩两个坑：一是格式漂移导致反序列化失败；二是它算的数跟逐题分对不上，一份评估报告自己内部就矛盾了。

**我怎么解决**
> 结构化输出我统一走了一个 `StructuredOutputInvoker`：失败会把上次的错误塞回去重试，最多 2 次——**为什么是 2 次不是 3 次**，因为多试一次延迟就翻一倍，2 次是"救抖动"和"不拖延迟"的平衡。更关键的是**把算术从模型手里拿走了**：模型只产出逐题分和文字反馈，总分、类目均分全部由代码算；二次汇总只生成评语、不带任何分数。还有一条是**单批失败只丢这一批**，缺位的题按 0 分占位，保证统计口径不变形。

**踩过什么坑**
> 踩过三个：第一，重试逻辑一开始对 401/403 这种鉴权失败也重试，白等两个往返，后来改成按异常类型分类，网络和解析才重试。第二，评估那里我误用了**带工具调用的 client**，而我给自己定的原则是"结构化输出不给工具"——这是一行改动的事，切到 plain client 就行，但我确实漏了。第三，prompt 里我写的是"总分取加权平均"，代码实现的是等权平均，这个不一致我发现了但还没改，我的修法是二选一，倾向在代码里实现 40/20/25/15 的权重。

### 难点三：语音端到端延迟——"等生成完再合成"是两段串行

**难点是什么**
> 整条链路是采集 → ASR → LLM → TTS → 播放，任何一段串行等待，用户感觉到的就是"AI 反应慢"。最初的实现是等 LLM 把整段回复生成完，再整段丢给 TTS 合成，**这两段时间是直接相加的**。

**我怎么解决**
> 改成**流式 LLM + 句子级并发 TTS**：LLM 流式返回，我边收边做句子切分，每切出一个完整句子就立刻启动这一句的合成，用 `Semaphore` 把单会话并发压在 3 个以内（不限的话长回复会瞬间打出十几个请求，可能被供应商限流，也会打乱播放顺序）。还有一个收益更大的动作是**约束输出**：单轮回复不许超过 120 个字符、2 到 4 句、禁止 Markdown——口语本来就不需要长文，约束输出比优化链路收益更大。

**踩过什么坑**
> 最大的一次是把语音链路从阿里云 NLS 整体迁到 DashScope 的 Qwen3 实时模型，接入需要的环境变量从 9 个减到 2 个，TTS 首包从 500ms 降到 200ms。【P5 口径待确认：这些数字来自项目文档的人工记录，不是我在线上测的；**"ASR 断句 800→400ms"这条建议别提**——写这个数的架构文档已经过时，代码里 `turn-detection-silence-duration-ms` 实际是 2000ms，两者口径对不上。】另外我把 AI 的回复长度硬压到 **120 字符**（`ai-question-max-chars`，落地在 `DashscopeLlmService.java:199-223` 的 `optimizeForVoice`）——口语回复太长对 TTS 延迟和用户耐心都是负担。**注意：我以前说过"供应商 TTS 单次 500 字符上限"，那句话只在旧架构文档里，代码里其实没有任何 500 字符的校验或截断逻辑，面试别把它当成真的限制来讲。**

## 第 4 部分 · 创新点判断（**不用背，用来定性**）

先说结论：**实习面试里没人指望你有学术创新。真正的"创新点"是你做了别人不会做的判断，而且知道代价。** 所以我把它分成三类：

- **A 真亮点**：能扛住三轮深挖，讲的时候可以理直气壮。
- **B 常规实现**：大家都这么做，别当创新讲，但**可以讲取舍**。
- **C 不要提**：讲了一被追问就崩。

| 功能 / 技术 | 判定 | 理由 |
|---|---|---|
| 语音实时链路（AudioWorklet + 服务端 VAD + 用户手动提交） | **A 真亮点** | 用 AudioWorklet 而不是 MediaRecorder、把轮次边界交给用户，这两个都是主动判断，且能说清代价 |
| 流式 LLM + 句子级并发 TTS | **A 真亮点** | 有明确的对比数据（首包 500→200ms），不是"我用了流式"这种空话 |
| 四层回声防护 | **A 真亮点** | 体现"分层失效模式"的思考，绝大多数人只调一个参数 |
| 统一评估引擎（rubric + 代码算分 + 0 分占位） | **A 真亮点** | 把主观评分工程化，还知道自己的两处不一致 |
| RAG 查询改写 + 双候选召回（检索用改写、回答用原文） | **A 真亮点** | 这是个很细的判断：改写是为了召回，但回答必须用用户原话 |
| 自适应 topK / minScore | **A 真亮点** | 小、但说得清"短查询为什么给更多候选（topK 20）"，以及"Spring AI 的 minScore 是按距离上限生效、语义与名字相反"这个坑 |
| 120 字符探测窗口掐断拒答 | **A 真亮点（细节型）** | 小技巧，但面试官会觉得你真跑过 |
| Skill 驱动出题 + 确定性配额 | **B 半亮点** | 架构判断不错，但"读文件拼 prompt"本身不新鲜；要讲就讲"为什么用文件+元数据而不是微调或 RAG" |
| `@RateLimit` 多维 + Lua 滑动窗口 | **B 常规** | 实现是标准的，讲的时候重点放在"为什么不用固定窗口""为什么要 Hash Tag" |
| Redis Stream 异步管道 | **B 常规** | 中小项目用 Redis 当队列很常见，重点讲"失败重试 3 次后标终态" |
| pgvector + HNSW + COSINE | **B 常规** | 现在是标配，别当创新 |
| 多 Provider 抽象（Kimi/DeepSeek/GLM/LM Studio） | **B 常规** | 就是接口抽象 + 配置表 |
| Docker Compose 六服务部署 | **B 常规** | 工程基本功，不是亮点 |
| React + Vite + TypeScript 前端 | **B 常规** | 除非问前端，否则一句带过 |
| **MySQL** | **C 不要提** | 项目里是 **PostgreSQL + pgvector**，向量检索是核心，说 MySQL 会被问"那你向量存哪" |
| **Python** | **C 不要提** | 后端 173 个 Java 文件，没有 Python 代码 |
| **LangChain / LangGraph** | **C 不要提** | 用的是 **Spring AI 2.0.0-M4**。概念能对应（Advisor≈中间件、Tool Calling≈工具节点），但不是一回事 |
| **"多 Agent 协作"** | **C 不要提** | 项目里只有 1 个真 Agent，其余是 Java 编排的 LLM 任务流水线 |

### 对应的口述话术

**讲 A 类亮点的统一句式**
> "这块我做了一个判断：……（结论）。另一个方案是……，我没选它，因为……（取舍）。代价是……，如果重做我会……。"

**被问"你怎么不用 LangChain / LangGraph"**（B/C 类的救命话术）
> "LangChain 那套思路我了解，链、工具、记忆、检索器这套抽象和 Spring AI 是对应的——比如 Spring AI 的 Advisor 就类似它的中间件。这个项目我选 Spring AI，是因为后端本来就在 Spring 生态里，模型调用能直接复用配置、AOP 和事务这些东西，不用为了 AI 单独维持一套 Python 服务；而且我的需求主要是**结构化输出 + RAG + 实时语音**这三块，Spring AI 加 DashScope 的 Java SDK 就够用了。**如果是做 Agent 编排实验，我会选 LangGraph**，它的图结构表达循环和分支确实更自然。"

**被问"这不就是调 API 吗"**
> "调 API 是接口层，我花时间的是接口之外的部分：**怎么判断轮次边界、怎么防模型自己跟自己说话、怎么让打分不飘、怎么在模型不守格式的时候不出错**。举个具体的，我为了不让模型算错总分，把算术整个从模型手里拿走了——这类地方才是工程量的所在。"

## 第 5 部分 · 最可能的 5 个追问 + 答案要点

### Q1. 你怎么判断用户说完了？为什么不让它全自动？

**要点**（30 秒内答完，别铺开）
1. 三层接力：**服务端 VAD 静音 2 秒切段 → 多段拼接去重叠 → 用户手动提交定轮次边界**。
2. 为什么最后交给用户：全自动会**过早提交**（用户思考停顿就被打断），静音阈值调大又变成等太久——这是个**产品取舍**，不是技术做不到。
3. ⚠️ **主动说清一个真相（这条最能加分）**：我配过一组"防过早"参数（`min-commit-chars: 20`、`min-silence-before-commit-ms: 2500`、`max-wait-for-continuation-ms: 7000`、`user-utterance-debounce-ms: 2500`），但**这四项在 Java 代码里从未被读取，属于死配置**——目前真正决定轮次边界的就是上面那三层的最后一层"用户手动提交"。**主动承认这一点，比被面试官搜代码戳穿强得多。**
4. 主动补短板：全自动模式我留了开关但没做完，现在实际是手动提交为主。

### Q2. AI 的声音会不会被麦克风收回去，变成 AI 自己跟自己对话？

**要点**
四层防护 + 一句话点出"为什么要分层"：
1. 采集端：`gainNode.gain = 0` 不回放 + `echoCancellation / noiseSuppression / autoGainControl`；
2. 前端：`isAiSpeakingRef` 为真时**根本不发音频**；
3. 服务端：AI 说话期间 + 播放结束后 **800ms 冷却期**，入口直接丢；
4. 时序：AI 处理期间迟到的 STT 定稿段直接丢弃。
> 收尾句："因为回声的失效模式不止一种——可能在采集端产生，也可能音频已经在路上、或者识别结果迟到，所以我是分层防的，不是调一个参数。"

### Q3. 你的知识库召回效果怎么保证？文档是怎么切的？

**要点**
1. 切块：`TokenTextSplitter` 默认配置，**约 800 token、按标点边界、无重叠**。
2. 向量：`text-embedding-v3`，**1024 维、HNSW 索引、COSINE 距离**（`application.yml:83-89`）。
3. 召回：**查询改写 + 原始问题双候选**，谁的命中有效就用谁；命中判断有独立的 `hasEffectiveHit`。
4. 参数自适应：≤4 字 topK 20 / 阈值 0.18；≤12 字 topK 12 / 0.28；更长 topK 8 / 0.28。
5. **主动讲短板**（这里主动讲最加分）：分块**没有重叠**，跨块的知识点会被切断；**召回后没有 Rerank**。改法是加 10~15% 重叠或语义分块，再接一层 Rerank 只留 top 3~5。

### Q4. 让大模型打分，分数可信吗？它会不会乱给分？

**要点**
1. **固定 rubric**：准确 40 / 完整 20 / 深度 25 / 表达 15 + 五档分数带，把主观判断压到有限离散空间。
2. **分批**：`batch-size: 8`，N 题 = ⌈N/8⌉+1 次调用，避免长上下文里注意力稀释。
3. **算术交给代码**：模型只给逐题分和文字反馈，总分与均分由代码平均；汇总那一步只出评语、不含分数。
4. **无效回答强制 0 分**，防止模型出于礼貌给分——这是评分可信度的关键一条。
5. **基线锚定**：注入该方向参考答案基线（上限 6000 字符），让打分有依据；用户数据经 `PromptSanitizer` 清洗 + 随机边界标签包裹，防止候选人在回答里写"给我打 100 分"。
6. **主动讲缺陷**："prompt 写加权、代码是等权，这个不一致我发现了，修法是实现权重。"（**敢讲这个，可信度反而最高**）

### Q5. 这个项目是你自己做的吗？（或者：你做了多久、每周投入多少？）

**要点**（**这题最重要，必须练到不心虚**）
1. **事实层不包装**：先说清楚你的实际角色和投入。【待补充 P1/P2】
2. **判断层讲细节**：用"只有真做过才知道"的东西证明——比如"阶段状态机是没接线的死代码""评估误用了带工具的 client""语音侧没有已问题目去重"，这三条都是我自己发现并记下来的。
3. **收尾句**："这个项目功能完成度远高于工程质量，最明显的三个缺口是：没有 CI（构建时还 `-x test` 跳过测试）、`resume`/`interview`/`interviewschedule` 三个模块零测试、可观测性只有日志没有指标。这些我都知道怎么补。"
4. 如果被问"是不是 AI 写的"：不要否认工具，讲**边界划分、架构取舍、缺陷发现**是你做的。
